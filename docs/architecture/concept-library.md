# 개념 탭: 정리 기준 ↔ 개념 라이브러리 (매니저앱)

매니저앱 "개념" 메뉴는 **정리 기준**(어떻게 정리할지)과 **개념 라이브러리**(정리한 결과)를 함께 보며 고치는 화면이다.
Think가 낸 작업 지시(2026-10-16)와 운영자 선택(개념 페이지는 기존 기록에서 계산, 출처·연결 저장 포함, Preview 생략)을 따른다.
Think 대화 연결은 `ai-think.md` §13, 정리 기준 참고는 §13.5.

## 1. 원칙

- 기존 개념 데이터(`concepts`, `concept_categories`)는 지우거나 옮기거나 자동으로 다시 분류하지 않는다.
  `concepts.kind`·`sub_type`(정의·정리)은 "기존 구분"으로만 보이고, 새 지식 분류로 쓰지 않는다.
- AI가 쓴 내용은 확정 기준이 되지 않는다. 확정은 운영자가 확정 창에서 직접 누를 때만 일어난다.
- 기본 틀(Bloom 지식 차원 4가지 등)은 "기본 틀" 초안으로만 들어간다. 코드가 특정 항목을 따로 다루지 않고, 만든 뒤에는 일반 항목과 같다.
- 연결·출처는 사용자가 직접 고른 것만 저장하고 보인다. 책 이름·쪽·원본 위치를 추정해 채우지 않는다.
  개념 초안(§7)을 확정할 때의 출처는 초안이 근거로 든 전사 블록의 쪽이다(모델이 쪽을 쓰지 않는다).
- AI가 만든 개념 초안과 폴더 제안은 운영자가 검토 화면에서 확정할 때만 라이브러리에 들어간다(§7).
- 검토 상태는 아직 기록하지 않는다. "전체 검토 완료" 같은 표시를 하지 않고, 기록하지 않는다고 화면에 적는다.

## 2. 화면

### 2.1 두 칸과 두 상태

- 2026-10-23부터 왼쪽은 **교육과정 흐름**(기준 과정 탐색도, `course-map.md`), 오른쪽은 개념 라이브러리로 자리를 고정한다.
  정리 기준은 거의 쓰지 않아 툴바 "정리 기준" 버튼의 창(`showConceptCriteriaDialog`, 기준 상세 그대로)으로 옮겼다.
  크게 보는 쪽(`ConceptWorkspaceFocus.courseMap` / `library`)만 바뀐다.
  - **흐름 중심**: 왼쪽 흐름 편집(목록 + 단원·과정 편집 + 저장 줄) 2/3, 오른쪽 라이브러리 요약 1/3.
  - **결과 중심**: 왼쪽 흐름 요약(읽기만) 1/3, 오른쪽 전체 라이브러리(트리 + 개념 상세) 2/3. 처음 들어오면 결과 중심이다.
- 바꾸는 방법은 요약 칸 머리의 "크게 보기", 또는 라이브러리 요약에서 개념 누르기다.
  본문 선택, 글 고치기, 출처 표시 누르기로는 바뀌지 않는다.
- 개념 상세의 이은 기준 칩을 누르면 그 기준을 고르고 정리 기준 창을 연다(칸은 그대로). 창에서 이은 개념을 누르면 창을 닫고 라이브러리에서 연다.
  창을 닫아도 기준 입력·선택은 컨트롤러에 남는다.
- 바꾸기·열기는 저장·확정·연결·AI 호출을 하지 않는다(`writes == 0` 시험).
- 라이브러리 요약은 현재 선택한 개념과 고른 기준에 이은 개념을 보인다.

### 2.2 상태 유지

- 선택(기준·개념), 크게 보는 쪽, 저장하지 않은 입력은 `ConceptLibraryController`가 갖는다. 메뉴는 화면을 갈아 끼우므로
  컨트롤러를 앱 전체에 하나 두어 다른 메뉴에 다녀와도 남게 했다. 앱을 끄면 저장하지 않은 입력은 남지 않는다.
- 칸마다 상세·요약을 둘 다 만들어 두고(`IndexedStack`) 보이는 것만 바꾼다. 네 칸과 대화 패널은 GlobalKey로 붙잡아,
  두 칸 ↔ 한 칸 배치가 바뀌어도 같은 위젯 상태(스크롤·커서·펼친 폴더)를 옮긴다.
- 숨은 칸도 다른 폭으로 다시 배치된다. 그래서 칸 안에서 폭에 따라 나란히/위아래로 바뀌는 부분(기준 목록·편집, 개념 트리·상세)도
  GlobalKey로 붙잡는다. 이게 없으면 접혀 있는 동안 스크롤과 펼친 폴더가 사라진다.
- 글자를 칠 때마다 컨트롤러가 알리지 않는다. "저장 안 됨" 표시는 항목마다 입력 칸을 직접 듣는다.

### 2.3 좁은 화면과 Think 대화

- Think 대화는 기존 개념 탭 대화 패널을 그대로 쓴다. 열려 있고 자리가 되면 오른쪽 옆(폭 = 영역 30%, 340~460)에 둔다.
  옆에 두면 남는 작업 영역이 440보다 좁아질 때는 옆에 두지 않고 칸으로 본다. 세 번째 고정 세로 영역을 억지로 만들지 않는다.
- 작업 영역이 880보다 좁으면 두 칸을 나란히 두지 않고 "교육과정 흐름 / 개념 라이브러리 / (Think 대화)" 칸 전환으로 한 칸씩 본다.
  겹치지 않고, 칸을 바꿔도 입력이 남는다.

### 2.4 저장 안 됨 표시

- 기준 목록 행과 편집 머리에 "저장 안 됨", 기준 창 머리에 "저장 안 됨 N", 고치는 중인 내용 칸 라벨 "내용 (저장 안 됨)".
- 저장 안 한 입력이 있으면 확정 버튼이 잠긴다(저장한 초안만 확정할 수 있다).

## 3. 정리 기준 저장

### 3.1 표

| 표 | 뜻 |
|----|----|
| `concept_criteria` | 기준 항목. 확정본(`title`, `body`, `version`, `confirmed_at`)과 저장된 초안(`draft_title`, `draft_body`, `draft_origin` = owner/template, `draft_saved_at`)을 따로 둔다. version 0 = 아직 확정한 적 없음 |
| `concept_criteria_revisions` | 확정 기록. 확정할 때마다 한 줄(판·제목·본문·메모) 쌓이고 고치거나 지우지 않는다 |
| `concept_criterion_links` | 사용자가 이은 기준–개념 (`criterion_id`, `concept_id`) |
| `concept_sources` | 사용자가 이은 개념 출처 (`concept_id`, `academy_id`, `book_id`, `grade_label`, `raw_page`, `display_page?`, `unit_path`, `page_order?`). `page_order`는 초안 확정 때만 채우는 쪽 안 등장 순서(1부터), 직접 이은 출처는 비어 있다 |

- 슈퍼관리자만 읽고 쓴다. 기준 표는 RPC로만 바뀐다(표 직접 쓰기 권한 없음). 연결·출처는 표에 직접 넣고 지운다.
  AI·Edge Function에는 이 표에 쓰는 경로가 없다(Edge는 읽기만).
- 출처를 넣을 때 `book_id`가 그 학원의 `resource_files`인지 확인한다. 같은 개념·책·학년·쪽은 한 번만 들어간다.

### 3.2 RPC와 동시 수정

| RPC | 하는 일 |
|-----|---------|
| `concept_criteria_create(title, body, origin)` | 새 항목을 **초안으로만** 만든다. `origin = 'template'`이면 기본 틀 초안 |
| `concept_criteria_save_draft(id, title, body, 판, 초안 시각)` | 초안 저장. 확정본은 그대로다. 확정본과 같은 내용으로 돌려 놓으면 초안을 비운다 |
| `concept_criteria_confirm(id, 판, 초안 시각, note?)` | 저장된 초안을 확정본으로 올리고(판 +1) 확정 기록을 남긴다 |
| `concept_criteria_discard_draft(id, 판, 초안 시각)` | 초안을 버린다. 확정한 적 없는 항목은 항목째 지운다(`{removed: true}`) |

- 모든 변경은 화면에 보였던 판(`version`)과 초안 저장 시각(`draft_saved_at`)이 지금과 같을 때만 된다. 다르면 `concept_criteria_stale`.
  앱은 초안 저장 시각을 서버가 준 문자열 그대로(마이크로초까지) 돌려보낸다.
- 막히면 앱은 친 글을 그대로 두고 최신 저장본만 다시 읽어, "다른 곳에서 바뀌었다"고 알린다. 다시 저장하면 최신 판 위에 저장된다.
- 고치던 기준이 다른 곳에서 지워졌으면 친 글을 "새 항목"(아직 저장 안 됨)으로 남긴다.
- 마이그레이션 전(표·RPC 없음)이면 기준 칸에 "DB에 정리 기준·연결·출처 저장소가 아직 없습니다" 안내와 다시 시도 버튼을 보인다.
  개념 라이브러리는 그대로 쓸 수 있다.

### 3.3 기본 틀

"기본 틀을 초안으로 넣기"는 같은 제목이 아직 없는 틀만 `origin = 'template'` 초안으로 만든다: 지식 분류 기준(개정 Bloom 지식 차원 4가지를
출발점으로), 노드 분리·통합 기준, 대표 용어와 다른 표현 처리, 개념 사이의 관계 정의, 확정 사례와 예외. 본문 첫 줄에 "아직 확정한 기준이
아닙니다"가 들어가고, 화면에는 "기본 틀" 배지가 붙는다. 고쳐서 저장하면 일반 초안(owner)이 되고, 확정은 따로 누른다.

## 4. 연결과 출처

- 기준–개념 연결: 기준 편집의 "열어 둔 개념 "X" 잇기", 개념 상세의 "고른 기준 "X" 잇기"로만 만든다. 칩을 눌러 상대 쪽을 열고,
  확인 창을 거쳐 연결만 끊는다(기준·개념은 그대로).
- 개념 상세는 "이은 정리 기준"을, 기준 편집은 "이 기준과 이은 개념"을 보인다. 없으면 "연결된 기준 없음"/"연결된 개념 없음",
  읽지 못하면 "읽지 못함"으로 구분한다. 사용자가 직접 이은 것만 보이고, 기준에 맞춰 검토했는지는 기록하지 않는다고 적는다.
- 출처: PDF 칸을 계속 띄우지 않는다. 개념마다 "출처 N개" 표시가 있고, 마우스를 올리면 책·쪽(최대 5개)을, 누르면 목록 창을 연다.
  누르기만으로도 열 수 있다(마우스 올리기에만 기대지 않음). 목록 행은 책 이름, 학년 · 단원 경로, 쪽("10쪽 (PDF 12쪽)" 또는 "PDF 12쪽"),
  "원본 열기", "출처에서 빼기"(확인 창)다. 출처 표시를 눌러도 크게 보는 쪽은 바뀌지 않는다.
- 저장 전 개념(임시 id)에는 연결·출처를 붙이지 않는다.

### 4.1 트리: 유형 순서와 주제 묶음

운영자 결정(2026-10-18): 라이브러리 트리를 새로 만든다. 칩 보기와 목록 보기를 둘 다 두고 고르게 한다(앱을 켠 동안 마지막 보기를 기억). 폴더 안 개념은
수학 순서로 늘어놓고, "이 개념을 이해하려면 바로 앞에 알아야 하는 개념"(주제 묶음)에 붙여 묶는다.

- **유형 순서**: `concept_types.sort_order`를 정의 → 표현 → 주의 → 성질 → 방법으로 바꾼다(마이그레이션 `20261018120000_concept_anchor_links.sql`).
  새 유형은 그 뒤, 유형 없는 개념(초안 확정 전 개념)은 맨 뒤다. 같은 유형이면 저장 순서(`sort_order`·만든 때)를 지킨다.
  폴더 안 순서 바꾸기(끌어 놓기)는 없앴다. 다른 폴더로 옮기기만 끌어서 한다.
- **주제 묶음 표** `concept_anchor_links`(개념마다 한 줄: `anchor_id`, 출처 `draft`/`proposal`/`manual`, 초안 id, 만든 사람). 여러 단계로 붙을 수 있다.
  같은 폴더끼리만 잇고 고리는 막는다. 개념을 지우면 그 줄도 지워진다. 운영자만 읽고, 쓰기는 `concept_anchor_set(p_links, p_origin)`
  (`proposal`·`manual`, 한 번에 여러 줄, 하나라도 어긋나면 아무것도 안 바뀜: `concept_anchor_bad_request`·`_not_found`·`_other_folder`·`_cycle`)과
  초안 확정 RPC로만 한다. 옮겨서 다른 폴더를 가리키게 된 줄은 지우지 않고 트리에서 쓰지 않는다(자동 정리 없음).
- **묶음을 정하는 세 곳**:
  1. 초안 정리(`concept_draft_organize.v3`): AI가 개념마다 `anchor`(같은 초안 개념 번호, 없으면 -1)를 낸다. 서버가 범위 밖·자기 자신·고리를 -1로 바꾼다.
     검토 창 카드의 "붙일 개념"에 보이고 고칠 수 있다(이 항목에 붙은 항목은 고를 수 없음, 뺀 항목·다른 폴더면 안내). 확정할 때
     같은 폴더의 남긴 항목끼리만 잇고(합쳐서 뺀 항목은 합친 쪽으로 한 번 따라감), 고리면 `concept_anchor_cycle`로 확정 전체를 막는다.
     Think 검토 대화도 저장된 묶음을 읽는다.
  2. 폴더 메뉴 "주제 묶음 제안받기"(`concept_draft_organize` task `anchors`, 프롬프트 `concept_anchor_plan.v1`): 앱은 폴더 id만 보내고, 서버가 그 폴더 개념
     (2~120개, 이름·유형·본문 앞 200자·지금 묶음)을 읽어 제안만 돌려준다(저장 안 함, `ai_runs` 기록). 답하지 않은 개념은 지금 묶음 그대로, 고리는 끊는다.
     창에서 줄마다 고르고 바꾼 줄만 `proposal`로 저장한다. 고른 대로면 고리가 생기면 저장을 막는다.
  3. 개념 상세 "주제 묶음" 칸: 붙은 개념, 이 개념에 붙은 개념을 보이고 "바꾸기"로 같은 폴더에서 고른다(`manual`).
- **보이기**: 칩 보기는 묶음 없는 개념을 흐름으로, 묶음은 둘레 상자(뿌리 → 붙은 개념, 겹 묶음은 안쪽 상자)로 그린다. 목록 보기는 들여쓰기와 꺾인 선이다.
  뿌리·형제 모두 유형 순서다. 묶음 표를 읽지 못하면(반영 전) 유형 순서로만 늘어놓고 상세에 알린다.
  머리의 찾기·유형 거르기는 개념을 숨기지 않고 흐리게 하며, 폴더 줄에는 유형 비율 막대와 개념 수를 둔다.

### 4.2 같은 개념의 여러 서술과 등장 위치

운영자 결정(2026-10-20): 중학교·고등학교나 여러 개념서에서 같은 개념이 다시 나올 때, 학년마다 개념을 복제하거나 나중 설명으로
앞 설명을 덮지 않는다. **개념**(안정된 id)은 그대로 두고, 그 개념을 설명하는 **서술**을 여럿 잇고, 교재·교육과정은 서술의
**등장 위치**로 둔다. 네 단계로 나눠 한다: 1 저장·조회, 2 개념 상세에서 서술 고르기·고치기·출처 보기, 3 Think가 고른 서술과
최신 저장본 읽기, 4 관계 판단(같은 개념의 다른 서술·확장·특수한 경우·검토 필요)과 초안 확정 때 고르기·변경 영향 표시.
1~3단계는 운영에 반영했다(마이그레이션 `20261020100000_concept_statements.sql`, `lib/services/concept_statement_service.dart`·
`concept_statement_store.dart`, 화면 `concept_statement_section.dart`·`concept_statement_dialogs.dart`, Think 읽기는 `ai-think.md` §13.2
`concept_reference` 3). **4단계도 했다**(마이그레이션 `20261020120000_concept_relations.sql` 2026-10-20 운영 반영,
`lib/services/concept_relation_service.dart`·`concept_relation_store.dart`, 화면 `concept_relation_section.dart`, 아래 "관계 판단").

- **개념 상세(2단계, Preview A안 선택 2026-10-20)**: 저장된 개념이면 본문 자리에 서술 칸을 둔다. 공통 내용이 있으면 맨 위
  "개념 공통 내용 · 모든 서술에 해당" 상자, 그 아래 "서술 N" 고르기 줄(기본(개념 본문) + 서술마다 칩), 고른 서술 하나만 펼친다.
  펼친 서술에는 확정본(확정 전이면 초안)과 상태·서술 방식·원문 그대로/정리함·원문 조건 표시, 적용 조건, 용어, 접힌 "원문과 보완한 점",
  그 서술의 등장 위치(더하기·빼기), "이 서술의 출처 N개"(누르면 출처 창, 출처마다 "어느 서술의 출처" 고르기)가 있다.
  기본 서술은 기존 "개념 본문 수정"과 "고친 기록"(`concept_content_revisions`)을 쓴다. 고른 서술은 개념별로 기억하고 저장하지 않는다.
- **서술 고치기 창**: 입력은 창이 들고 있고, "초안 저장"만 서버에 보낸다(확정본 그대로). "확정"은 저장된 초안이 있고 저장 안 한 입력이
  없을 때만 누를 수 있고 확정 메모를 받는다. 그사이 바뀌었으면(`stale`) 입력을 남긴 채 최신 저장본을 다시 읽어, 다시 저장하면 그 입력이 초안이
  되거나 "최신 저장본 불러오기"로 입력을 버린다. 확정 전 서술의 초안 버리기는 서술을 지운다(출처·등장 위치가 붙어 있으면 서버가 막음).
- **트리**: 기본 서술을 뺀 서술이 있는 개념은 칩·목록 줄 이름 뒤에 겹 아이콘과 서술 수(기본 포함)를 붙인다. 수는 트리를 읽을 때
  `concept_statements`(role statement)에서 세고, 상세에서 다시 읽거나 서술을 더하고 지우면 바로 바뀐다. 표를 읽지 못하면 표시하지 않는다.
- **Think가 읽기(3단계)**: Think 대화 참고로 고른 개념이면, 그 개념 상세에서 고른 서술의 id만 함께 보낸다(기본 서술이면 보내지 않음).
  서버가 보낼 때마다 공통 내용·서술 목록(제목·상태)·고른 서술의 확정본과 저장된 초안·등장 위치·서술별 출처를 다시 읽는다.
  고르지 않은 서술의 본문은 읽지 않는다. 대화 패널의 참고 개념 줄에 보낼 서술이 보이고, 답변 뒤 서버가 읽은 서술 상태(확정 판·초안·
  못 찾음·읽지 못함)를 알린다. 서버가 아직 모르는 버전이면 기본 서술이 아닌 서술을 고른 채로는 보내지 않는다. Think는 서술을 고치거나
  확정하지 못한다(쓰는 길이 없다).

- **기존 개념은 옮기지 않는다.** 개념 본문(`concepts.content`)이 그 개념의 "기본 서술"이고, 서술 표에는 더하는 서술만 들어간다.
  기존 출처는 `statement_id`가 비어 있어 기본 서술의 출처로 남는다. 이름·학년으로 합치거나 나누지 않는다.
  `concepts.family_id`·`version_label`(이름이 똑같으면 같은 묶음, `기본-2`…)은 예전 이름 묶음이고 서술과 관계없다
  (2026-10-20 운영 DB: 개념 1,373개 중 40개가 `기본-2` 이상, 예: 분배법칙 4개. 자동으로 합치지 않는다).
- **`concept_statements`**: `role = 'core'`(개념 공통 내용, 개념마다 하나: 공통 의미(필수)·적용 범위·공통 조건) 또는
  `'statement'`(서술: 제목·본문(필수), 서술 방식, 이 서술의 적용 대상·조건, 원문에 조건이 적혀 있는지(`stated`/`omitted`/`check_context`),
  필요한 용어, 원문 그대로인지 우리가 정리한 글인지(`verbatim`/`organized`, 기본 organized), 원문 또는 원문 참조, 보완·수정한 부분과 이유,
  확인되지 않은 사항). 정리 기준(§3)과 같이 확정본(`content`·`version`)과 저장된 초안(`draft`, 출처 `owner`/`ai`)을 따로 두고
  RPC로만 바꾼다: `concept_statement_create(개념, 역할, 내용)`(초안으로만), `_save_draft`, `_confirm`(판 +1, `concept_statement_revisions`에 한 줄),
  `_discard_draft`(확정 전이면 줄째 지우되 출처·등장 위치가 붙어 있으면 `concept_statement_in_use`). 모두 화면에서 본 판·초안 시각이 같을 때만 된다
  (`concept_statement_stale`). 내용은 서버(`concept_statement_clean`)가 검사하고 같은 모양으로 맞춰, 확정본과 같게 저장하면 초안이 빈다.
  확정한 서술을 지우는 길은 없다. 서로 다른 서술은 따로 남고, 한 서술의 오타 수정은 그 서술의 다음 판이다.
- **출처**: `concept_sources.statement_id`(비면 기본 서술). `concept_source_set_statement(출처, 서술|null)`로만 바꾼다. 같은 개념·책·학년·쪽은
  지금처럼 한 번만 들어가므로 한 쪽은 한 서술에만 붙는다. 다른 개념의 서술·공통 내용은 가리키지 못한다(트리거).
- **교육과정 등장 위치** `concept_appearances`: 교육과정 판(문제은행과 같은 코드, 모르면 비움 = "교육과정 판 미기록")·학교급(초/중/고)·
  학년/과목 이름·단원 경로·메모, 서술(비면 기본 서술). 운영자가 직접 넣고 지운다(고치기 없음). 새 교육과정을 더해도 이전 줄은 남는다.
  교재 정보(`textbook_metadata.payload`)에는 교육과정 판이 없어서 교재에서 끌어오지 않는다(`payload.version`은 교육과정 판이 아니다).
  2026-10-23부터 기준 과정 탐색도의 단원을 가리키는 줄(배치, `course_unit_id`)도 이 표에 있다. 판·학년·단원 경로는 탐색도에서 채우고
  상세에 "기준 단원"(Think 카드로 놓였으면 "Think 배치") 배지로 보인다. 넣기·옮기기는 탐색도 화면에서만 하고, 여기서 빼면 그 단원에서도 빠진다
  (`course-map.md` §6). 마이그레이션 전 DB에서는 예전 열만 읽는다.
- **기본 서술 고친 기록** `concept_content_revisions`: 개념 이름·본문을 고치면 고치기 전 값이 남는다(트리거, 순서·폴더만 바꾸면 남지 않음).
- 모두 슈퍼관리자만 읽는다. AI·Edge는 이 표에 직접 쓰지 않는다. 2026-10-23부터 운영자가 승인한 Think 카드만 승인 RPC로 개념 만들기·
  이름·본문·유형·폴더 고치기·서술 고치기·지우기(붙은 것이 없을 때만, §4.4)·배치를 한다. 고친 기록의 이유는 "Think 카드 승인: 이유"다(`course-map.md` §7).
  마이그레이션 전이면 앱 서비스가 `not_ready`로 알린다.

**4단계: 관계 판단** (운영자 결정 2026-10-20: 관계 다섯 가지, 다른 서술은 확정 전 서술로 붙이기, 정하지 않으면 검토 필요로 넣기,
같은 이름은 한 쌍씩 검토, Preview 없이 바로)

- **관계는 운영자가 고른 것만 남는다.** 이름·학년·문장이 비슷하다는 것만으로 관계를 넣거나 개념을 합치거나 옮기지 않는다.
  "같은 개념"으로 판단해도 두 개념은 그대로 두고 판단만 기록한다(합치기는 없다).
- **`concept_relations`**: 개념 → 기준 개념, `kind` = `extends`(기준 개념을 넓힌 개념) · `special_case`(기준 개념의 특수한 경우),
  `origin` = `draft`(초안 확정 때 고름) · `review`(검토 필요를 판단하며) · `manual`(상세에서 직접). 같은 쌍은 한 줄이고, 반대 방향 줄이
  있으면 막는다(`concept_relation_reverse_exists`). RPC `concept_relation_set`·`concept_relation_remove`로만 바꾼다.
  (2026-10-23 유형 여섯 개·맥락·근거·결정 기록·이력·Think 관계 카드로 넓혔다. 두 옛 유형의 규칙은 그대로다. §4.6)
- **`concept_reviews`**: "같은 개념인지 검토 필요" 표시. 이유 `same_name`(확정 때 같은 이름이 이미 있음) · `overlap`(폴더 제안 AI가 겹칠 수
  있다고 봄, 상대 없이 AI 메모만) · `draft`(초안 검토에서 검토 필요로 고름) · `manual`. 열린 표시는 같은 쌍에 하나다(`concept_review_open`).
  `concept_review_resolve(표시, 판단, 상대, 메모, 반대 방향)`로 닫는다: `different` · `same` · `extends` · `special_case`.
  확장·특수한 경우로 닫으면 관계 한 줄이 생긴다(반대 방향이면 "상대 → 표시된 개념"). 닫힌 줄은 판단 기록으로 남는다.
  `concept_review_decide_pair(개념, 상대, 판단, 메모)`는 같은 이름 검토 창의 한 쌍 판단이다(열린 표시가 없으면 만들고 바로 닫음, 반대쪽 열린 표시도 닫음).
- **초안 확정 때 고르기**: 검토 카드마다 "기존 개념과"(정하지 않음 · 새 개념 · 기존 개념의 다른 서술 · 확장 · 특수한 경우 · 검토 필요)와
  기존 개념(라이브러리에서 찾기). 검토 항목에 `relation: {kind, concept_id, concept_name}`로 저장하고 확정 RPC는 `concept_id`만 본다
  (`concept_name`은 표시용).
  - 다른 서술: 새 개념을 만들지 않고 고른 개념에 **확정 전 서술**(`concept_statements` role statement, 초안 `draft_origin` = 그대로면 `ai`,
    고쳤으면 `owner`, 서술 방식 `organized`)로 더한다. 그 항목의 출처 쪽은 그 서술에 이어(`statement_id`) 고른 개념에 붙고, 이미 같은 책·학년·쪽
    출처가 있으면 그 출처는 그대로 두고 건너뛴다(`sources_skipped`). 기존 확정 내용·개념 본문·유형·폴더는 바꾸지 않는다. 유형·폴더·주제 묶음은 쓰지 않는다.
  - 확장·특수한 경우: 새 개념으로 넣고 "새 개념 → 고른 개념" 관계(`origin draft`)를 남긴다. 검토 필요: 새 개념으로 넣고 표시(`reason draft`, 상대는 고르면 남김).
  - 새 개념: 표시 없이 넣는다. **정하지 않음**: 새 개념으로 넣고, 이 초안 전 라이브러리에 이름(앞뒤 공백·대소문자 무시)이 같은 개념이 있으면
    `same_name`(가장 먼저 만든 개념이 상대), 없고 폴더 제안에 겹침이 있으면 `overlap`으로 표시한다. 확정을 막지 않는다(한 번에 확정도 그대로 된다).
  - 검토 창·한 번에 확정 창은 확정 전에 고른 관계 수와 "검토 필요"로 들어갈 항목(같은 이름·겹침)을 보인다. 같은 이름은 앱이 미리 찾고(정확한 이름),
    확정 RPC가 다시 본다. 관계 표가 없는 DB(마이그레이션 전)면 관계를 고른 검토는 확정하지 않는다(옛 확정 RPC가 관계를 무시하기 때문).
- **개념 상세 "다른 개념과의 관계" 칸**: 열린 검토 필요(이유·비교할 개념·판단하기·비교할 개념 열기), 관계 줄(누르면 그 개념 열기, 빼기),
  지난 판단(최근 5건). "검토 필요로 표시"(상대를 고르거나 상대 없이), "관계 더하기"(개념 고르기 → 판단 창). 판단 창은 판단·방향·이유를 받고
  "기록할 판단" 문장을 보인 뒤 기록한다. 머리에 "검토 필요" 배지, 트리 칩·목록 줄에 깃발.
- **같은 이름 검토 창**(개념 라이브러리 머리 "같은 이름 검토"): 이름이 같은 개념 묶음마다 한 쌍씩 지금 판단(판단 전·검토 필요·기록한 판단)과
  "판단하기/다시 판단". 기본은 판단 전 쌍만 보인다. 자동으로 합치거나 옮기지 않는다.
- **변경 영향 표시**: 개념 본문·서술·공통 내용 고치기 창 맨 위에 "붙은 것"(출처·다른 서술·등장 위치·이은 기준·관계·검토 필요 수)과
  "고쳐도 이것들은 자동으로 바뀌거나 옮겨지지 않습니다"를 보인다. 읽지 못한 항목은 세지 않았다고 적는다.
- 관계·검토 표는 슈퍼관리자만 읽고, 쓰기는 RPC로만 한다. Edge·AI에는 쓰는 길이 없다. Think 검토 대화 참고(`concept_draft_reference`)는
  아직 항목의 관계를 보여 주지 않는다(후속). Think 변경 카드를 승인해도 `concept_draft_item_norm`이 관계를 남긴다.

### 4.3 여러 교재의 설명을 한 개념에 모으기

운영자 결정(2026-10-20): 같은 부분을 다른 교재에서 뽑으면 설명이 조금씩 다르다. 교재마다 원문(근거)은 그대로 두고,
개념마다 **대표 서술 하나**를 보인다. 대표 서술은 지금의 **기본 서술(`concepts.content`)** 자리를 그대로 쓴다(앱·Think·Edge가 모두 이 열을 읽는다).
AI가 여러 교재를 보고 만든 글은 **수정안**까지만 되고, 운영자가 이유를 적어 확정해야 대표 서술이 된다. 여러 책에 나온다는 것만으로
맞는 설명으로 보지 않고, 이름·문장 비슷함만으로 같다고 정하지 않는다. 기존 본문이 원문인지 정리한 글인지는 새로 붙이지 않는다.
네 단계로 한다: 1 대표 서술 확정본·수정안 나누기와 고친 이유, 2 출처 근거 범위(전체·일부·관련·미확인)와 근거 블록 잇기
(같은 쪽이 대표와 보조 설명을 함께 뒷받침할 수 있게 출처 제약을 쪽+서술로), 3 새 교재 비교(출처만 연결·대표 수정안·보조 설명·새 개념 후보·보류)와 승인,
4 Think가 수정안·근거 범위를 읽기. **1단계는 했다**(마이그레이션 `20261020140000_concept_content_drafts.sql`, 2026-10-20 운영 반영).
**2단계는 했다**(아래 "출처 근거 범위", 2026-10-20 운영 반영·`concept_draft_organize` 재배포).
3단계 결정(2026-10-20): 초안 검토 항목에 "출처만 연결"(기존 개념의 기본 서술이나 고른 서술에 쪽만 잇고 글은 만들지 않음)과
"대표 수정안"(기본 서술에 출처를 잇고 항목 글을 기본 서술 수정안으로 저장, 확정은 1단계 창에서 이유를 적어서)을 더한다. 대표 수정안을 고른
개념에 이미 수정안이 있으면 확정을 막고 기존 수정안을 먼저 확정하거나 버리라고 안내한다(덮어쓰지 않음). "보류"는 이번 확정에 넣지 않고
초안 기록에 보류로 남겨 "보류한 항목" 목록에서 나중에 다시 처리한다. 검토 카드에 기존 개념 비교 칸을 두고, AI 비교 제안(항목마다 갈래와 이유,
고른 줄만 검토에 반영)도 이번에 넣는다. **3단계는 했다**(아래 "새 교재 비교", 2026-10-20 운영 반영·`concept_draft_organize` 재배포).

- **`concept_content_drafts`**(1단계): 개념마다 수정안 하나(본문·고치려는 이유·`origin` `owner`/`ai`·저장 시각). 수정안을 쓸 때 화면에 보였던
  본문의 md5(`base_md5`)를 같이 둔다. RPC `concept_content_save_draft(개념, 본문, 이유, 본 본문 md5, 본 저장 시각)`: 그사이 본문이 바뀌었으면
  `concept_content_stale`, 수정안이 바뀌었으면 `concept_content_draft_stale`, 지금 본문과 같은 글이면 수정안을 지운다.
  `concept_content_confirm(개념, 저장 시각, 이유)`: 이유가 꼭 있어야 하고(`concept_content_note_required`), 수정안을 쓴 뒤 본문이 바뀌었으면
  (개념 수정 창 등) `concept_content_base_changed`로 막는다. 지금 본문과 비교해 다시 저장하면 새 바탕이 된다. 확정하면 본문을 바꾸고 수정안을 지운다.
  `concept_content_discard_draft(개념, 저장 시각)`. 1단계에는 `ai` 수정안을 넣는 길이 없다(3·4단계에서 운영자가 승인한 제안으로만).
- **고친 기록**: `concept_content_revisions`에 `via`(`direct` 수정안 없이 바로 고침 / `draft` 수정안 확정)·`note`(고친 이유)·`draft_origin`.
  확정 RPC가 같은 거래 안에서 트리거에 이유를 넘긴다. 이 마이그레이션 전 줄은 개념 수정 창으로 바로 고친 것이라 `direct`·이유 없음이다.
  개념 수정 창(이름·종류·본문 함께)은 그대로 바로 고친다(이유 없음).
- **화면**(1단계): 개념 상세에서 기본 서술을 고르면 본문 아래에 저장된 수정안 상자(확정 전·작성자·저장 시각·이유·본문, 바탕이 바뀌었으면 알림)와
  "수정안 쓰기/열기" 버튼. 수정안 창은 왼쪽에 지금 기본 서술(확정본), 오른쪽에 수정안 입력, 아래에 이유. 저장한 뒤에만 확정할 수 있고 확정은 이유를 받는다.
  머리에 "수정안 있음" 배지. 개념 수정 창은 수정안이 있으면 "바로 고치면 수정안을 다시 비교해 저장해야 한다"고 알린다. 고친 기록 창은 바로 고침/수정안 확정과 이유를 보인다.
  수정안 표가 없는 DB(마이그레이션 전)면 서술은 그대로 보이고 수정안 자리에 "저장소가 아직 없습니다"만 보인다.
- Think는 아직 수정안을 읽지 않는다(기본 서술은 확정본만 읽는다, 4단계).
- **출처 근거 범위·근거 블록**(2단계, 마이그레이션 `20261020160000_concept_source_evidence.sql`, 2026-10-20 운영 반영): `concept_sources`에
  `evidence_scope`(`whole` 전체 근거 / `part` 일부 근거 / `related` 관련 설명 / `unknown` 범위 미확인, 기본 `unknown`)·`evidence_note`(500자)·
  `evidence_origin`(`owner` / `ai` = 운영자가 AI 제안을 받아들임)·`evidence_basis_md5`(정할 때 본 서술 글)·정한 시각·사람, 근거 블록
  `draft_id`·`block_ids`(원문 글은 복사하지 않고 초안 기록 `prepared.blocks`를 가리킨다). 기존 출처는 모두 `unknown`이고 범위를 추정해 채우지 않는다.
  - 출처 한 줄 단위를 (개념, **서술**, 책, 학년, 쪽)으로 바꿨다(예전 (개념, 책, 학년, 쪽) 제약을 빼고 `coalesce(statement_id, 0…)` 고유 색인).
    같은 쪽이 기본 서술과 다른 서술을 함께 뒷받침할 수 있다. 같은 서술에 같은 쪽은 하나다(옮길 때 겹치면 "이미 그 서술의 출처" 안내).
    교재 순서 보기는 개념별로 묶으므로 같은 쪽이 두 줄이어도 개념·쪽은 한 번이다(그 쪽 안 순서를 아는 줄을 쓴다).
  - 초안 확정 RPC가 출처를 넣을 때 그 쪽의 근거 블록을 함께 적는다. 이 마이그레이션 전에 확정한 초안은 한 번 `concept_source_link_draft`로
    잇는다: 확정 결과(`result.concepts`의 index·key·id·statement_id)마다 검토 항목 `blocks`(없으면 AI 초안 `source_blocks`)를 쪽별로 나눠,
    개념·서술·책·학년·쪽이 모두 맞고 아직 블록이 없는 출처에만 넣는다. 확정 뒤 다른 서술로 옮긴 줄, 직접 이은 줄은 비워 둔다.
  - `concept_source_basis(개념, 서술)`: 출처가 뒷받침하는 글. 기본 서술이면 개념 본문, 서술이면 확정본(없으면 초안)의 제목·본문·적용 조건.
    `concept_source_evidence(개념)`(운영자): 서술별 글·md5와 출처별 범위·메모·누가 정했는지·"정한 뒤 서술 바뀜"·근거 블록 글.
    `concept_source_set_evidence(출처, 범위, 메모, 본 범위 시각, origin, 서술 md5)`: 본 시각이 다르면 `concept_source_evidence_stale`,
    `ai`는 제안이 본 서술 md5가 지금과 다르면 `concept_source_basis_changed`. 표에 직접 고치는 길은 없다. 범위를 정한 뒤 서술이 바뀌어도 범위를
    자동으로 되돌리지 않고 "정한 뒤 서술 바뀜"으로만 알린다.
  - AI 제안: `concept_draft_organize` `task: 'evidence_scope'`(`concept_id`, `statement_id`). 서버가 위 RPC로 서술 글·근거 블록을 읽어
    출처마다 범위·이유·근거에 있는/없는 부분을 제안하고 저장하지 않는다(프롬프트 `concept_source_scope.v1`, `ai_runs` 기록). 근거 블록이 없는
    출처는 보내지 않는다(`no_blocks`). 범위만 보고 설명의 옳고 그름이나 교재 우열은 판단하지 않는다.
  - 화면: 출처 창(640)에서 출처마다 "근거 범위: …" 배지(전체 `kThinkSuccess`·일부 `kThinkLink`·관련 `kThinkSub`·미확인 `kThinkHint`,
    툴팁에 누가 언제 정했는지)·"AI 제안 승인"·"정한 뒤 서술 바뀜" 배지, "범위 정하기"(범위 칩 4개 + 메모), "근거 문장 N개 보기"(교재 쪽을 읽은 글이며
    정리한 서술이 아니라고 표시). 위에 서술마다 "근거 범위 제안받기". 제안은 출처 줄 아래에 "AI 제안: …"과 받아들이기·버리기로 보이고, 받아들인 줄만
    저장된다. 창을 닫으면 받아들이지 않은 제안은 사라진다. 근거 저장소가 없는 DB면 범위 칸 대신 "저장소가 아직 없습니다"만 보인다.
- **새 교재 비교**(3단계, 마이그레이션 `20261020180000_concept_draft_compare.sql`, 2026-10-20 운영 반영): 검토 항목 관계(`relation.kind`)에 셋을 더했다.
  셋 다 새 개념이 아니라서 유형·폴더·붙일 개념을 쓰지 않는다(`ReviewItem.noNewConcept`).
  - `source` 출처만 연결: `relation.concept_id`의 기본 서술(또는 그 개념의 다른 서술 `relation.statement_id`)에 이 항목의 근거 쪽만 출처로 잇는다
    (근거 블록 포함, 범위 `unknown`). 글·서술·본문은 만들거나 바꾸지 않는다. 이미 같은 서술의 출처인 쪽은 건너뛴다(`sources_skipped`).
    서술이 그 개념의 다른 서술이 아니면 `concept_draft_relation_statement_not_found`.
  - `revise` 대표 서술 수정안: 기본 서술에 출처를 잇고 항목 글을 `concept_content_drafts`에 넣는다(`base_md5` = 지금 본문, 그대로 둔 글 `ai`·
    고친 글 `owner`, 이유 칸에 교재·단원·항목 이름). 본문은 1단계 창에서 이유를 적어 확정해야 바뀐다. 그 개념에 수정안이 이미 있으면
    `concept_draft_revise_draft_exists`로 확정 전체를 막는다(덮어쓰지 않음, 앱은 확정 전에 미리 알린다). 본문과 같은 글이면 수정안을 만들지 않는다.
  - `hold` 보류: 이번 확정에 넣지 않고 `concept_draft_holds`(초안·항목 key·항목 스냅숏·근거 블록·`open`/`reopened`/`dropped`)에 남긴다. 보류만 있어도
    확정된다. `concept_draft_holds_open()`이 열린 것(다시 연 초안을 버려 돌아온 것 포함)을, `concept_draft_hold_reopen(초안)`이 같은 초안 기록
    (쪽 전사·AI 초안·폴더 제안)으로 새 검토 초안(`holds_of`)을 만들어 보류 항목만 관계·붙일 개념을 비워 넣는다. `concept_draft_hold_drop(보류, 이유)`.
  - 확정 결과에 `linked`(출처만)·`revises`(만든 수정안)·`holds`를 더하고, 결과 개념 줄은 `relation` `source`·`revise`(`content_draft`)로 남는다.
  - `concept_compare_targets(개념 id[])`(운영자, 읽기만): 폴더·본문·md5·다른 서술(확정본 또는 초안 글)·출처 줄 수·책·수정안 유무.
  - AI 비교 제안: `concept_draft_organize` `task: 'compare'`(`draft_id`). 서버가 **저장된 검토**(없으면 AI 초안)를 읽고, 항목마다 후보
    (고른 기존 개념·같은 이름·폴더 제안의 라이브러리 겹침, 최대 3개)를 위 RPC로 읽어 new·statement·source·revise·hold 중 하나와 이유·다른 점을
    제안한다. 후보가 없는 항목은 보내지 않고(`no_candidates`), 한 번에 12개까지다. 저장하지 않는다(프롬프트 `concept_draft_compare.v1`, `ai_runs`).
    이름만으로 같다고 하지 않고, 애매하면 보류, 수정안이 있는 후보엔 revise를 고르지 않게 지시한다.
  - 화면: 검토 카드 관계 목록에 "기존 개념에 출처만 연결"·"기존 개념의 대표 서술 수정안"·"보류(이번에 넣지 않음)". 출처만 연결은 "이을 서술"
    (기본 서술·다른 서술)을 고른다. 기존 개념을 고른 관계면 "…과(와) 비교"로 그 개념의 폴더·출처 수·책·수정안 있음·기본 서술·다른 서술을 읽기 전용으로 본다.
    아래 단추 "기존 개념과 비교 제안"은 저장한 검토에서만 받고, 카드마다 "AI 비교 제안"에 반영·무시가 있으며 반영은 저장 전 편집이다.
    개념 초안 목록의 "보류한 항목"에서 초안 기록별로 "N개 다시 검토"(새 초안을 연다)·항목별 "버리기"(이유 선택). 3단계 DB가 없으면
    출처만·수정안·보류를 고른 검토는 확정하지 않는다(한 번에 확정에서도 그 초안만 뺀다).

### 4.4 개념 지우기

운영자 결정(2026-10-23, 개념 라이브러리 정리 1단계): **붙은 것이 하나도 없는 개념만 지운다.** 어느 길로 지우든 DB가 같은 기준으로 막는다.

- **붙은 것** = `concept_attachments(개념)`: 출처, 서술, 등장 위치, 기준 단원 자리(배치), 관계(나가는·들어오는 줄), 같은 개념 검토(표시된 쪽·상대 쪽),
  범위별 검토 기록(§4.5),
  정리 기준 연결, 주제 묶음(묶이는 쪽·앵커 쪽), 수정안, 유형 연결, 본문 고친 기록, 열린 교재 초안 검토가 "기존 개념과"로 고른 대상(뺀 항목·닫힌 초안은
  세지 않음), 바로가기, 운영 지시문, 그리고 이 목록에 없는 새 외래키(`other`). `total`이 0일 때만 지울 수 있다. 미리 보기(`concept_delete_check`)·
  Think 개념 읽기(`get_concept_for_edit`의 `deletable`·`delete_blocked_by`)·Think 개념 카드 미리 보기·승인·실제 삭제가 모두 이 함수 하나를 쓴다.
- **막는 곳**: `concepts` BEFORE DELETE 트리거. 로그인한 운영자가 아니면 내용 없이(`concept_delete_forbidden`), 붙은 것이 있으면 종류·개수를
  `detail`에 실어(`concept_delete_attached`) 거절한다. 앱 RPC(`concept_delete`)·표 직접 삭제(REST)·service role·Think 카드가 모두 이 트리거를 지난다.
  `auth.uid()`가 없는 길(service role·DB 관리 작업)은 운영자 검사를 건너뛰지만 붙은 것 검사는 그대로 한다.
- **동시에 붙는 경우**: 개념을 가리키는 외래키는 모두 `on delete restrict`다(전에는 cascade). 센 뒤 그사이 자료가 붙어도 지우기가 실패하고
  자료가 남는다. 지우는 쪽이 먼저 끝나면 붙이는 쪽이 외래키 오류로 실패한다(잃는 자료 없음). 열린 초안의 대상은 외래키가 없어서, 그사이 지워지면
  초안 확정이 `concept_draft_relation_target_not_found`로 막힌다. 승인 대기 Think 카드는 붙은 것으로 세지 않고 승인 때 다시 확인한다.
- **폴더 지우기**: 폴더(하위 폴더 포함)에 개념이 하나라도 있으면 `concept_folder_not_empty`(개념 수)로 막는다. 전에는 폴더를 지우면 안의 개념과
  붙은 자료가 함께 지워졌다. 빈 폴더만 지운다. 폴더를 지우면 그 폴더에 둔 바로가기 줄은 지금처럼 함께 지워진다(개념은 그대로).
- **앱**: 개념 지우기는 먼저 미리 보고, 붙은 것이 있으면 "삭제할 수 없음" 창에 종류·개수를 보이며 지우기 단추를 주지 않는다. 미리 보기를 못 읽으면
  지우지 않는다(0개로 보지 않음). 확인한 뒤 그사이 붙으면 서버 거절 내용으로 같은 창을 보인다. 마이그레이션 전 DB면 `not_ready`로 알리고 지우지 않는다
  (예전 표 직접 삭제로 돌아가지 않는다).
- **하지 않는 것**: 붙은 개념을 강제로 지우는 기능, 출처·기록·유형 연결을 먼저 지워 조건을 맞추는 기능, 중복 개념 자동 삭제·합치기.
  중복으로 보여도 붙은 것을 옮길 방법(합치기)이 아직 없으므로 "병합 필요, 삭제 보류"로 둔다.
- **영향**: 교재 초안·Think 카드로 만든 개념은 모두 유형 연결이 있고, 2026-10-20 이후 본문을 고친 개념은 고친 기록이 있어 지울 수 없다.
  지울 수 있는 것은 예전에 직접 만든 뒤 아무것도 붙지 않은 개념뿐이다. Think 개념 카드의 지우기도 대부분 막힌다(카드에 막힌 이유가 보인다).
  자동으로 생기는 연결이라도 예외로 빼지 않는다(운영자 결정).

### 4.5 범위별 개념 검토

운영자 결정(2026-10-23, 개념 라이브러리 정리 2단계): Think가 라이브러리를 빠짐없이 훑고, 개념마다 **범위를 나눠** 무엇을 봤고 무엇을 찾았는지
기록으로 남긴다. 기록은 사용자가 승인한 항목만 남고, 개념 본문·폴더·관계는 바꾸지 않는다. 마이그레이션 `20261023160000_concept_review.sql`.

- **범위 5개**: `notation`(오탈자·표기), `meaning`(수학적 의미·조건·범위), `classification`(유형·폴더), `unit`(중복·개념 단위), `relations`(관계).
  한 범위를 봤다고 다른 범위까지 본 것으로 치지 않는다.
- **결과 5개**: 문제 못 찾음(`no_issue_found`)·문제 있음·비교 더 필요·확인 못 함·병합 필요(삭제 보류, `unit`에서만). "검증됨"은 없다.
  문제 못 찾음은 "이번에 본 범위에서 못 찾음"일 뿐이다. 병합 필요는 기록이고, 합치거나 지우지 않는다.
- **저장**: `concept_quality_reviews`. 같은 개념인지 판단하는 `concept_reviews`(§4.2)와 다른 표다. 항목마다 확인한 것·찾은 것·근거·확인 못 한 것·
  더 할 일, 비교한 개념(`compared` = id·이름·그때 글 지문)·더 비교할 개념, 검토한 판(`marks`)과 그 범위 지문(`mark`), 카드 id·항목 번호·제안 시각·승인자.
  운영자만 읽고, 쓰는 길은 Think 카드 승인(`course_think_apply_review`) 하나다. 기록은 고치거나 지우지 않고 쌓는다.
- **판(지문)**: `concept_review_marks(개념)` = 글(이름·본문·확정한 서술 id와 판), 분류(유형·폴더 경로), 관계(나가는·들어오는 관계 줄과 상대 개념의 글 지문).
  `revision`은 세 지문의 앞 12자를 이은 것이다. notation·meaning·unit은 글, classification은 분류, relations는 관계 지문을 본다.
  기록 뒤 그 범위의 지문이 바뀌면 상태에 `stale`(다시 검토 필요)로 보이고, 예전 기록은 이력으로 남는다. 확정 전 서술 초안, 폴더 안 순서, 바로가기,
  검토 기록 저장은 지문을 바꾸지 않는다.
- **순회 목록** `concept_review_walk(walk_id, filter, offset, limit)`: 처음 부를 때 조건(폴더(하위 포함)·유형(`유형 없음` 포함)·이름·배치 여부·
  검토 상태와 범위)에 맞는 개념 id를 폴더 경로·폴더 안 순서·이름·id 순으로 고정해 `concept_review_walks`에 둔다(30일 지난 것은 새로 만들 때 지움).
  이어 읽기는 `walk_id`와 `offset`만 쓰므로 그사이 이름·폴더가 바뀌어도 빠지거나 겹치지 않는다. 지워진 개념은 `missing`으로, 시작 뒤 생긴 개념은
  `created_after` 수로 따로 알린다. 한 번에 40개(최대 60), 본문 없이 요약(앞 120자·글자 수·서술·출처·배치·관계·같은 이름 수·판·범위별 상태)만 준다.
  배치되지 않은 개념도 들어가고, 배치 후보 목록을 대신 쓰지 않는다.
- **상태** `concept_review_status(ids)`(1~20개): 범위마다 최신 기록 전부, 앞선 기록 5개 요약, 기록 수, 승인 대기 중인 카드 항목.
- **개념 읽기**: `concept_think_detail`에 출처(300개까지, 이은 서술 id), 교육과정 등장 위치, 관계(방향·종류·상대), 같은 개념 검토(20개, 열린 것 먼저),
  판, 범위별 상태, 서술 판을 더했다.
- **카드** `concept_review_record`(항목 20개까지): 제안 때 Think가 읽은 `revision`이 그 범위의 지금 지문과 같아야 한다(`concept_review_stale`).
  승인은 고른 항목만, 항목마다 따로 한다. 승인 때 그 범위 지문이 다르거나, 비교한 개념의 글이 바뀌었거나 지워졌으면 그 항목은 남기지 않는다
  (`concept_review_stale`·`concept_review_compared_changed`). 카드 화면은 `course-map.md` §7과 같은 항목 카드다.
- **지우기와의 관계**: 범위별 검토 기록은 붙은 것(`quality_reviews`)이라, 기록이 하나라도 있는 개념은 지울 수 없다(§4.4, 자동 연결도 예외 없음).
  같은 개념 검토 표시(`reviews`)도 열린 것·끝낸 것 모두 두 개념에 붙은 것이다. 운영자 결정(2026-10-23): 검토 기록은 보존하고, 병합 필요와 열린 같은
  개념 검토는 그 개념의 지우기를 막는다. 다른 범위·같은 범위의 새 검토, 개념 글 고침(다시 검토 필요), 시간 경과, 같은 개념 검토 끝내기로 막힘을
  풀지 않는다. 검토를 끝내도 기록이 남으면 §4.4의 "붙은 것이 없는 개념만 지우기"가 그대로다. 지우려고 기록을 없애지 않고, 보관·안전한 병합은
  따로 할 후속 작업이다(§8).
- **하지 않는 것**: 기록 고치기·지우기, 검토 기록으로 본문·폴더·관계 바꾸기, 병합 실행, Think가 스스로 전체 검토 시작, 임베딩 유사도.
  중복 후보는 이름 검색·같은 이름 수로만 찾고, 같은 개념인지는 본문·서술·출처를 읽고 비교한 근거로만 판단한다.

### 4.6 관계 유형

운영자 결정(2026-10-23, 개념 라이브러리 정리 3단계): 관계 유형을 여섯 개로 하고, 맥락·근거·결정 기록·이력을 남기며, Think는 관계를 읽고
관계 카드로 제안만 한다. 마이그레이션 `20261023180000_concept_relation_types.sql`.

- **읽는 법**: 모든 관계는 방향이 있고 "A(`concept_id`, 출발) → B(`related_id`, 기준)"로 읽는다. A→B, B→C가 있어도 A→C로 넓혀 읽지 않는다.
- **유형 6개**
  - `kind_of`(종류·특수화): A는 B의 한 종류. `part_of`(구성·부분): A는 B를 이루는 요소.
  - `derived_from`(근거·유도): A는 B를 근거로 유도·증명된다. **맥락 필수**(어떤 유도인지).
  - `depends_on`(학습 의존): A를 배우거나 쓰려면 B가 필요하다. **맥락 필수**(어떤 목표·방법에서인지). 과정 순서만으로 넣지 않는다.
    화면·Think 문장은 "맥락 …에서: …"로 맥락을 앞에 둬, 조건 없는 선수 관계처럼 보이지 않게 한다.
  - `extends`(확장)·`special_case`(특수한 경우): 예전부터 쓰던 유형. 그대로 두고, `special_case`와 `kind_of`는 따로 둔다
    (옛 관계를 이름만 바꿔 옮기지 않는다).
- **한 쌍의 규칙**: 한 쌍에 다른 유형은 함께 둘 수 있다. 같은 쌍·유형·맥락(앞뒤 공백·대소문자 무시)은 하나다(`concept_relation_exists`).
  `kind_of`·`part_of`는 같은 유형의 반대 방향을 막고, `depends_on`·`derived_from`은 맥락이 다르면 반대 방향을 둔다(`concept_relation_reverse_exists`).
  고리는 검사하지 않는다. 두 옛 유형은 예전 규칙 그대로(같은 방향 한 줄, `concept_relation_set`은 그 줄의 유형을 바꿈, 반대 방향 막음).
- **칸**: 맥락(300자)·근거(1000자)·메모(500자), 결정(`decided_by`·`decided_at`·`decided_via` = draft·review·manual·think·`action_id`),
  판단 때 두 개념의 글 지문(`judged_marks`), 판(`rev`, 고칠 때마다 오름)·`updated_at`. 생긴 곳(`origin`)과 정한 길(`decided_via`)은 다르다
  (초안으로 생긴 관계를 Think 카드로 고치면 생긴 곳은 draft, 정한 길은 think). 이 기능 전에 생긴 관계는 "결정 기록 없음"으로 보인다.
- **다시 검토**: 판단 뒤 두 개념 중 하나의 글(이름·본문·확정 서술, `concept_review_text_mark`)이 바뀌면 "다시 검토 필요"로 보인다. 판단 때 기록이 없으면 모름.
- **이력** `concept_relation_events`: 넣기·바꾸기·빼기마다 전·후 상태, 그때 두 개념 이름, 길, 카드·항목, 이유·불확실한 점. 개념 id에 외래키가 없어
  이력은 개념 지우기를 막지 않는다(§4.4의 붙은 것에 들지 않음). 운영자만 읽고 쓰는 길은 관계 RPC뿐이다.
- **RPC**: `concept_relation_list(개념)`(관계·관계 범위 검토 상태·승인 대기 카드 항목·최근 이력 20개·이력 수, 운영자만),
  `concept_relation_save(id, rev, …)`(직접 넣기·고치기, 고칠 때는 읽은 판이 같아야 함·같은 관계가 있으면 막음),
  `concept_relation_remove(id, rev)`(관계만 지움, 판을 주면 같을 때만). 옛 `concept_relation_set`·`concept_relation_remove(id)`도 그대로 쓴다.
- **개념 상세 관계 칸**: 관계 줄에 유형 아이콘·문장(맥락 포함)·근거·"유형 · 정한 길/결정 기록 없음"·"다시 검토 필요"·"Think 카드 승인 대기 N",
  고치기·빼기. "관계 더하기"는 개념 고르기 → 관계 창(유형 6개·방향·맥락·근거·메모, 또는 "서로 다른 개념/같은 개념" 판단만). 고치기는 같은 창에서
  읽은 판으로 보낸다(그사이 바뀌었으면 막고 지금 것을 다시 읽음). 아래에 관계 이력(최근 5줄). 초안 확정 때 고르기·같은 개념 판단 창은 그대로다.
- **Think**: `get_concept_relations`(관계·문장·맥락·근거·결정·다시 검토·승인 대기·이력, 40개씩)와 `propose_concept_relation_change`
  (카드 `concept_relation_change`, 넣기·바꾸기·빼기 20개까지, 항목마다 두 개념의 글 판·바꾸기/빼기는 관계 판, 이유 필수·불확실한 점).
  제안 때 판·유형·맥락·겹침·같은 카드 안 중복을 검사한다. 승인은 고른 항목만, 빼기 → 바꾸기 → 넣기 순서로 항목마다 따로 하고, 그때 두 개념의 글이
  제안 때와 다르거나(`concept_relation_concept_stale`) 관계 판이 다르면(`concept_relation_stale`) 그 항목은 반영하지 않는다. 빼기는 관계만 지운다.
  카드는 두 개념(이름·폴더·id)·지금과 바꾼 뒤·방향 문장·근거·불확실한 점·이유, 열린 같은 개념 검토 표시, 다른 대기 카드를 보인다.
  자동 확정은 없다. 두 개념에 열린 같은 개념 검토가 있어도 카드를 막지 않고 알린다(승인해도 검토 표시는 닫히지 않는다).
- **하지 않는 것**: 과정 순서로 학습 의존 넣기, 이름·문장 유사도로 관계 넣기, 옛 관계 일괄 전환, 고리 검사, 관계를 따라 개념 옮기기·합치기.

### 4.7 Think의 출처 원본 다시 읽기

    통합 완료와 1차 검수 3조건은 목록을 한 번 돌며 개념마다 지문을 한 번 구해 상태와 1차 판정에 넘긴다. 상태 반환만으로 1차 판정을 대신하지 않는다. 완료·3조건·조건별 합계·분모·대기·미결의 기준은 바꾸지 않는다. 운영이 8초 안에 끝난다는 보장은 아니다. 운영의 시간 초과 원인은 이 진단이 기록되기 전에는 미확인이다.

## 5. 개념책 불러오기

DB에 이미 있는 교재 구조와 문항 기록만 쓴다. 새 업로드는 하지 않는다. 쪽을 AI로 옮겨 적는 일은 소단원 카드의
"개념 초안 만들기"를 누를 때만 한다(§7).

- 책 목록: `textbook_metadata`(최대 500행)의 책·학년 항목. 이름은 `resource_files.name`을 볼 수 있을 때만, 아니면 "(책 이름을 볼 수 없음)".
  "개념서만"이 기본으로 켜져 있고, `textbook_type = '개념서'`이거나 `payload.series`의 시리즈 기본 종류가 개념서(개념원리·개념원리 중등·
  개념+유형)인 항목을 보인다. 저장된 종류는 바꾸지 않고 배지로 그대로 보인다(비어 있으면 "종류 미지정", 시리즈가 있으면 "X 시리즈").
  항목마다 소단원 수와 문항 기록 수(`textbook_problem_crops` 개수만, 4개씩)를 보인다.
- 같은 책이 항목 둘로 저장된 경우가 있다(2026-10-16 운영 DB 확인: 개념+유형 6개 학년, 개념원리 공통수학1·2). 예전 교재 탭으로 등록한
  항목은 종류가 개념서이고 문항 기록이 없으며, 교재 등록 마법사로 등록한 항목은 시리즈 키와 문항 기록이 있다. 둘 다 단원을 보이고,
  이름·학년이 같은 항목은 시리즈 항목을 먼저 둔다. 고른 항목에 문항 기록이 없고 같은 이름·학년 항목에 있으면 그 항목으로 옮겨 보는
  버튼을 보인다. 항목을 합치지는 않는다.
- 예전 항목 숨김(2026-10-19 운영자 결정. 개념+유형 1-1 예전 항목 `b9c6c37b…`는 문항 기록 0개·PDF 연결 legacy로 확인): 문항 기록이 0개이고,
  지금 목록(필터 적용 뒤)에 함께 보이는 이름·학년이 같은 항목에 문항 기록이 있으면 목록에서 숨긴다. 문항 기록 수를 다 센 뒤에 정해지고,
  세지 못한 항목(-1)은 숨기지 않는다. 같은 이름 항목의 수도 함께 센다. 목록 아래 "같은 교재의 문항 기록 없는 예전 항목 n개 숨김 · 보이기"로
  다시 볼 수 있다. 화면에서만 숨기고 `textbook_metadata`·`textbook_units`·학생 연결 설정은 지우거나 옮기지 않는다.
- 단원: 중단원마다 `sub_units[]`(이름 있는 것)가 있으면 그것을, 없으면 `smalls[]`를 저장 순서대로 쓴다. `smalls` 중 `sub_key`가 없는 것은
  예전 교재 탭이 저장한 실제 소단원이고, 있는 것은 문항 묶음(A·B·C…)이라 "문항 묶음" 배지를 달고 개념 페이지 표시를 하지 않는다.
  이름·`start_page`·`end_page`·`is_exercise`(연습문제 배지)는 저장된 값 그대로이고, 연습문제 여부를 이름으로 짐작하지 않는다.
  쪽은 PDF 쪽(raw)이고 `page_offset`은 쓰지 않는다(운영 DB의 문항 기록은 모두 `raw_page = display_page`, `page_offset`은 비었거나 0).
  범위가 없으면 "쪽 범위 없음", 80쪽이 넘으면 앞 80쪽만 보인다.
- 쪽 표시(운영자 결정 "derive"): 소단원 범위 안에 `textbook_problem_crops`가 하나라도 있으면, 문항이 없는 쪽은 "개념 페이지",
  있는 쪽은 "문항 N개"다. 범위 안에 문항 기록이 하나도 없으면 아직 추출 전일 수 있어 표시하지 않는다. 항목 전체에 문항 기록이 없으면
  그 사실을 위에 한 번 알린다. 본문 쪽 번호는 그 쪽 문항 기록의 `display_page`가 있을 때만 보인다.
- 쪽을 최대 6개 골라:
  - **원본 열기**: 본문 PDF의 서명 URL을 `#page=N`으로 외부 앱에서 연다(뷰어가 지원하면 그 쪽).
  - **"X" 출처로 잇기**: 열어 둔 저장된 개념에 고른 쪽을 `concept_sources`로 넣는다. 책·학년·쪽·본문 쪽·단원 경로는 저장된 값 그대로다.
  - **Think 대화에 쪽 이미지 붙이기**: 대화가 연결돼 있고 첨부 자리가 있을 때만. 본문 PDF를 임시 폴더에 한 번 받아(내용 해시별)
    고른 쪽을 PNG(긴 변 1600)로 만들어 기존 첨부 경로로 올리고, 입력창에 책·학년·단원·쪽 줄을 채운다. 보내기는 사용자가 누른다.
- 초안 진행(초안을 만들 수 있는 창에서만): 창을 열 때 `concept_drafts`의 검토 중·확정 행 위치(교재 항목·`unit_path`·상태)만 한 번 읽는다
  (최대 5000행, 본문은 읽지 않음). 소단원은 교재 항목(학원·책·학년)과 단원 경로가 같아야 같은 것으로 보고, 이름으로 짐작해 잇지 않는다.
  소단원 상태는 확정 초안이 있으면 "초안 확정함", 없고 검토 중 초안이 있으면 "초안 검토 중", 아니면 "초안 안 함"이다. 버림·다시 정리함은 세지 않는다.
  진행률 = 초안을 만든(검토 중+확정) 소단원 ÷ "개념 초안 만들기"를 누를 수 있는 소단원(쪽 범위 있음, 문항 묶음·연습문제 아님)이고,
  모두 만들기 전에는 100%가 되지 않게 내림한다. 책 목록 항목·쪽 칸 위 진행 상자·중단원 머리에 보이고, "초안 안 한 소단원만"으로 거를 수 있다.
  검토 중 소단원은 "개념 초안 만들기" 대신 "검토하기"(가장 최근 검토 중 초안을 연다), 확정한 소단원은 "다시 만들기"(새 초안이 하나 더 생김)다.
- 차례로 만들기(운영자 요청 2026-10-17): 중단원 머리의 네모로 중단원을 여러 개 고르면, 초안이 없고 20쪽 이하인 소단원을 한 번에 하나씩
  전사 → 정리 → 폴더 제안한다(동시에 돌리지 않음). 확정은 하지 않는다. 시작 전에 예상 비용을 보이고 확인을 받는다.
  시작할 때마다 초안 기록을 다시 읽어 이미 초안이 있는 소단원은 건너뛴다(응답이 끊겨 서버에만 초안이 생긴 경우 두 번 만들지 않음).
  한 소단원이 실패하면 다음으로 넘어가고, 예산 초과·AI 설정 없음·권한·가림 영역 불일치는 다음도 같은 이유로 실패하므로 남은 것을 멈춘다.
  요청 제한(분당 횟수)이면 65초 기다렸다가 같은 단계를 한 번 다시 한다. 폴더 제안만 실패하면 초안은 남는다(검토 화면에서 폴더를 정함).
  "멈추기"는 지금 소단원까지 하고 멈추고, 앱이 돌리는 것이라 창을 닫을 수 없다. 다시 시작하면 남은 것만 한다.
- 한 번에 확정("개념 초안" 목록, 차례로 만들기 창): 운영자 결정(2026-10-19): 초안 정확도가 높아 세부 검수 없이 한 번에 확정하고,
  쓰면서 라이브러리에서 고친다. 목록에서는 검토 중인 초안을 모두 고를 수 있고, 차례로 만들기 창은 다 만든 뒤 "만든 초안 n개 한 번에 확정"으로
  그 창에서 만든 초안만 넣는다(건너뛴 소단원·예전 초안은 넣지 않음). 검토를 저장한 초안은 저장된 검토로, 저장하지 않은 초안은 AI 초안·폴더 제안
  그대로(처음 검토: 이름·내용·유형·폴더·주제 묶음) 쓴다. 확정 전에 초안을 다시 읽어 검토 화면의 확정과 같은 검사(`reviewProblem`)를 하고,
  확정할 초안("AI 초안 그대로" 표시)·막힌 초안과 이유·새로 만드는 폴더(여러 초안에서 같은 경로는 하나, 이름순이라 비슷한 이름이 붙어 보임)·새 유형을
  한 창에 보인다. AI 초안 그대로는 폴더 제안이 없거나 영역 밖이거나, 새 유형을 받아들일지 정하지 않았거나, 이름·내용이 빈 개념이 있으면 막힌다
  (검토 화면에서 정한다. 새 유형을 앱이 대신 받아들이거나 거절하지 않는다). 운영자가 확인 창에서 누를 때만, AI 초안을 그 초안의 검토로 저장
  (`concept_draft_save_review`, 저장한 적 없을 때만)한 뒤 기존 `concept_draft_confirm`(저장 시각 확인)으로 초안마다 차례로 확정한다.
  하나가 실패해도 앞서 확정한 것은 남는다. 같은 이름 폴더·유형은 RPC가 다시 쓰므로 초안끼리 부딪히지 않는다.
  직렬로 만들어 폴더 이름은 앞 초안을 이어 쓰지만, 개념을 뽑는 정리 단계는 다른 초안·라이브러리를 보지 않으므로 같은 개념이 두 초안에 생길 수 있다.
  이것은 아래 겹침 안내로 알리기만 한다.
- 초안끼리 폴더 이름 맞추기(운영자 결정 2026-10-17, `concept_folder_plan.v2`): 폴더 제안 때 서버가 같은 학원의 다른 검토 중 초안
  (최근 30개)이 쓰기로 한 자리를 읽어 함께 보여 준다. 검토를 저장했으면 운영자가 정한 폴더(뺀 개념 제외), 아니면 그 초안의 AI 폴더 제안이다.
  AI는 그중 라이브러리에 없는 폴더를 이미 있는 폴더처럼 보고 같은 이름을 다시 쓴다. 차례로 만들기에서 뒤 소단원이 앞 소단원의 새 폴더를 이어 쓴다.
  앱은 지금처럼 초안 id만 보낸다(다른 초안 내용은 서버가 DB에서 읽음).
- 겹치는 개념은 알리기만 한다(같은 결정): 폴더 제안 AI가 라이브러리나 다른 초안과 같은 개념으로 보이는 것을 `folder_plan.overlaps`
  (개념 번호, 상대, 이유)에 적는다. 초안은 고치지 않는다. 검토 창 개념 카드에 "겹칠 수 있음"으로, 한 번에 확정 창에 남기는 개념의 겹침과
  고른 초안끼리 같은 이름으로 남은 개념(앱이 직접 셈, 확정하면 같은 개념의 다른 판)으로 보인다. 검토 창 Think 대화도 항목마다 이 안내를 읽는다.
  Think가 마지막에 여러 초안을 직접 고치는 방식은 하지 않는다(초안 변경은 카드로 제안하고 운영자가 승인).
- 교재 순서로 보기(운영자 결정 2026-10-18 "store_order"): 라이브러리는 수학 구조로 묶고, 교재는 그 개념을 다른 순서로 꺼낼 수 있다
  (라이브러리 1·2·3·4가 교재에서는 4·1·2·3). 진행 상자의 "교재 순서로 보기"는 고른 교재 항목(학원·책·학년)의 `concept_sources`를 읽어
  개념마다 처음 나온 쪽 → 쪽 안 순서(`page_order`) → 이름순으로 다시 늘어놓고, 단원 경로가 바뀔 때마다 단원 제목을 단다. 폴더는 바꾸지 않고 보이기만 한다.
  `page_order`가 없는 출처(이 열을 더하기 전에 확정한 것)는 그 초안 기록(`prepared.blocks` 쪽별 순서, 검토 항목 `blocks` 또는 AI `source_blocks`,
  `result.concepts`의 개념 id)으로 볼 때마다 계산하고 DB에 채워 넣지 않는다. 그래도 모르면(직접 이은 출처 등) 같은 쪽 개념 뒤에 두고 "쪽 안 순서 모름"으로 보인다.
  같은 이름이 다른 교재에서 다시 나와 새 판(`기본-2`)이 된 개념은 판마다 따로 보인다. 공식 교육과정 순서표는 없다(교재 순서만).

## 6. Think 대화

- 개념 탭 대화 패널은 기존 대화에만 이어지고, 대화를 새로 만들지 않는다. 기존 메시지와 제안 카드는 그대로 보인다.
- 대화 패널에 "참고 개념"과 "참고 기준"이 보인다. 고른 기준 id만 보내고, 서버가 보낼 때마다 확정본과 저장된 초안을 나눠 다시 읽는다.
  저장하지 않은 편집은 보내지 않는다. 서버가 읽은 결과(읽음·잘림·없음·오류·건너뜀·옛 서버)를 패널에 그대로 알린다.
- 자세한 규칙은 `ai-think.md` §13(개념)과 §13.5(정리 기준).

## 7. 개념 초안(개념책 소단원 → 라이브러리)

운영자 결정(2026-10-16): 시범(개념+유형 1-1, 8–20쪽 전사 비교, 8–13쪽 정리)을 보고 OpenAI 기본 모델로 쪽마다 두 번 전사,
DB에 저장, AI가 지금 라이브러리 상태를 보고 폴더 구조를 제안해 임시로 넣고 운영자가 확인·수정한 뒤 확정한다.
대·중·소단원은 참고일 뿐이고 실제 수학 구조에 맞춘다. 정리 모델은 기본(primary).

흐름(소단원 카드 "개념 초안 만들기" → 진행 창 → 검토 화면):

1. **쪽 전사**(`concept_page_read`, 저장 방식): 앱이 본문 PDF 쪽을 긴 변 1900px PNG로 그리고, 그 쪽 문항 기록
   (`item_region_1k`, 없으면 `bbox_1k`)을 회색 상자 M1… 로 가린다. 서버는 같은 규칙으로 문항 기록에서 가림 영역을 다시 만들어
   앱이 그린 것과 다르면 409로 막고, 책 이름·인쇄 쪽도 서버가 읽는다. 쪽마다 두 번 읽어 `concept_page_transcripts`
   (쪽·회차·지시문 판마다 한 줄)에 저장하고, 이미 있는 회차는 다시 읽지 않는다.
2. **정리**(`concept_draft_organize` task `create`): 앱은 쪽 번호만 보낸다. 서버가 저장된 전사를 읽어 두 번 읽기를 맞추고(쪽 장식 제외,
   글자·숫자가 다른 곳과 한쪽에만 있는 블록 표시) 고른 정리 기준(id만, 확정본·초안 구분)과 개념 유형 목록(§7.1)으로 개념 초안·
   유형·새 유형 제안·결과 요약·뺀 블록·질문을 만든다. 검사(모르는 블록 id, 어디에도 안 쓴 블록, 근거 블록에 없는 수식, 근거 없는 개념,
   목록에 없는 유형)를 붙여 `concept_drafts`에 저장한다. AI에 준 유형 목록도 `concept_drafts.concept_types`에 남긴다.
3. **폴더 제안**(task `folders`): 지금 라이브러리 폴더 경로·개념 이름과 초안 개념을 주고, 영역(최상위 폴더) 아래 넣을 경로를 받는다.
   교재 단원은 참고로만 준다. 영역 밖·빠진·겹친 배치와 새로 만들어질 폴더를 계산해 `folder_plan`에 저장한다. 실패해도 초안은 남고
   "이어서 다시 하기"는 폴더 제안만 다시 한다.
4. **검토**: 결과 요약, Think 질문, 검사, 개념 유형(새 유형 받아들이기·거절, 기존 구분 고르기), 폴더 제안 설명과 폴더 트리
   (새 폴더 표시, 새 폴더 이름 바꾸기), 개념 카드(이름·내용 고치기, 유형 고르기, 그대로·고쳐서·빼기, 폴더 고르기·경로 직접 쓰기, 확인 필요·수식 경고, 근거 블록·두 번 읽기 차이,
   원본 쪽 이미지에서 잘라 보기). 이름·내용을 고치면 "고쳐서"가 된다. 검토는 저장한 것만 남는다(`concept_draft_save_review`,
   저장 시각으로 덮어쓰기 막음). AI 결과(초안·근거·검사·폴더 제안)는 고치지 않는다.
   초안·전사는 수식을 `$…$`·`$$…$$`로 쓰므로 개념 내용·근거 블록·변경 카드·개념 목록은 `LatexTextRenderer(dollarMath: true)`로 2차원으로 그린다
   (학습앱 `normalizeTodoSheetMath`와 같은 규칙). `$`가 글자일 수 있는 다른 화면은 켜지 않는다.
5. **확정**(`concept_draft_confirm`): 저장된 검토만 쓴다(저장 안 된 편집이 있으면 앱이 먼저 저장). 한 번에(하나라도 어긋나면 아무것도 안 들어감)
   - 폴더: 영역 이름부터 경로를 따라 같은 이름 폴더가 있으면 쓰고 없으면 만든다(깊이·순서는 부모 기준). 기존 폴더·개념은 바꾸지 않는다.
   - 유형: 받아들인 새 유형을 `concept_types`에 더한다(같은 이름이 이미 있으면 그것을 쓰고 기존 구분은 바꾸지 않는다).
     개념마다 유형이 확정된 유형이어야 한다(없으면 `concept_draft_type_required`, 목록에 없거나 거절한 유형이면 `concept_draft_unknown_type`).
   - 개념: 기존 구분(`sub_type`)은 유형의 기존 구분, 정의 → `kind = definition`, 연산·정리 → `theorem`, `level = 1`.
     `concept_type_links`에 유형을 잇는다. 같은 이름 묶음(`concept_families`)에 넣고 판 이름은 비어 있는 `기본`, `기본-2` … 중 첫 것.
   - 출처: 근거 블록의 쪽마다 `concept_sources`(인쇄 쪽은 전사 기록 값, 단원 경로는 초안의 교재 단원, `page_order`는 그 쪽 준비 블록 중
     근거 블록이 처음 나온 자리). 근거 블록이 없으면 출처 없이 들어가고 확정 창에 알린다.
   - 초안을 `confirmed`로 닫고 만든 개념·폴더 id를 남긴다. 교재 학원 소속이 아니면 확정하지 못한다.
6. **버리기**(`concept_draft_discard`): 초안만 닫는다. 쪽 전사는 남아 다시 만들 때 쓴다.

접근: 두 표는 운영자만 읽고, 쓰기는 Edge 함수(서버 키)와 위 RPC로만 한다. 앱은 OpenAI를 직접 부르지 않는다.
개념 탭 위 "개념 초안" 버튼에서 검토 중인(또는 모든) 초안을 다시 연다. 비용 안내는 시범 실측 대략값(읽기 한 번 약 $0.018,
정리+폴더 제안 약 $0.09, 12쪽 기준)이다. 한 번에 20쪽까지이고(운영자 결정 2026-10-17: 12쪽 넘는 소단원도 나누지 않고 한 번에 만든다.
앱 `kConceptDraftMaxPages`·Edge `MAX_PAGES`·DB `concept_drafts_pages_check`가 같은 값), 12쪽을 넘으면 정리 출력 한도를 24000 → 32000으로 늘린다.
정리 시간(운영자 결정 2026-10-18): 모델이 초당 60~70토큰쯤 써서 140초로는 결과 9천~1만 토큰이 한계였고, 내용이 많은 소단원은
다시 해도 같은 자리에서 끊겼다. 그래서 create·rerun 은 200과 머리를 먼저 보내고 10초마다 공백을 흘린 뒤 결과 JSON(원래 상태 코드는
`http_status`)을 붙이며, AI 호출 한도는 330초다(Supabase 응답 시작 150초 제한을 피함, 함수 전체 시간은 유료 요금제 400초 안).
요금제 한도에 걸려 응답이 끊기면 앱은 "응답이 중간에 끊겼다"(`response_cut`)로 알린다. 쪽 읽기·폴더 제안은 140초 그대로다.
쪽 읽기는 보통 10~30초인데 가끔 응답이 아예 멈춰 140초에 끊긴다(2026-10-19, 1,800자 쪽이 토큰 0으로 끊김). 그래서 앱은 그 읽기
하나만 한 번 더 읽고(`isConceptDraftTimeout`: `Signal timed out.`·`response_cut`), 또 끊기면 실패로 알린다.

백그라운드 정리(운영자 결정 2026-10-19): 330초로도 끊기는 소단원이 나왔다(기본 도형 "점, 선, 면, 각" 8쪽, 블록 115개·읽기 한 번 약 2.9만 자로
지금까지 가장 많음). 같은 양을 써도 모델 속도가 초당 23~74토큰으로 세 배까지 달라서, 쪽 수로는 시간을 미리 알 수 없고
함수 실행 한도(400초) 안에서 더 늘릴 수도 없다. 그래서 지금 앱은 create·rerun 에 `background: true`를 붙인다.
- 서버는 입력을 읽고 맞춘 뒤 OpenAI 백그라운드 모드(`background: true`, `store: true`)로 정리를 시작하고, 작업을
  `concept_draft_jobs`(마이그레이션 `20261019100000`)에 적은 뒤 바로 `job_id`를 돌려준다. 정리 입력(맞춘 블록·기준 이름·유형)은
  작업에 두고, 결과를 받을 때 다시 읽지 않는다. 한 사람이 동시에 돌리는 작업은 3개까지다(넘으면 `rate_limited`).
- 앱은 5초마다 `task: 'collect'`로 묻고, 기다린 시간을 진행 글에 붙인다("개념 초안을 정리하는 중 (2분 11초 지남)").
  결과 확인이 잠깐 실패하면(`ai_poll_failed` 등) 5번까지 다시 묻는다. 앱은 25분까지 기다린다.
- 끝난 결과는 `running → saving`으로 바꾼 한 요청만 저장해 초안이 두 번 생기지 않는다(저장하던 요청이 2분 넘게 소식이 없으면 이어받는다).
  저장·검사·사용량 기록은 바로 부른 정리와 같은 함수(`finishOrganize`)를 쓴다. 다시 정리 작업이면 이때 지금 초안을 닫는다.
- 결과를 받으면 OpenAI 쪽 응답을 지운다(`DELETE /responses/{id}`). 20분 넘게 끝나지 않은 작업은 취소하고 `ai_timeout`으로 둔다.
  OpenAI가 5분 넘게 시작조차 안 한 작업(`queued`)은 그때 취소하고 `ai_stalled`로 둔다(2026-10-20, 14일 136번 중 2번이 토큰 없이 20분을 채움).
  서버가 이 둘로 끊은 초안 만들기는 앱이 같은 쪽으로 한 번만 새로 시작한다("멈춘 정리를 다시 하는 중"). 앱이 25분 기다리다 멈춘 것과
  다시 정리(`rerun`)는 새로 시작하지 않는다(서버 작업이 아직 돌거나 카드가 처리됐을 수 있다).
  원본 PDF 주소·내려받기는 연결 끊김·5xx·게이트웨이의 `fetch failed`일 때만 1초·3초 뒤 두 번 더 해 본다(링크 없음·저장소 이전 전은 바로 알림).
  OpenAI에 남는 것은 교재 전사·정리 지시문·결과뿐이고 학생 정보는 없다. 백그라운드가 아닌 호출은 그대로 `store: false`다.
- `background` 없는 요청(옛 앱)은 위 330초 길 그대로이고, 새 앱은 옛 서버가 바로 준 `draft_id`도 그대로 받는다.
연습문제·문항 묶음 범위에는 버튼을 두지 않는다.

### 7.1 개념 유형

운영자 결정(2026-10-17): 개념을 정의·정리·연산(기존 구분)보다 세세하게 나눈다. AI가 초안을 만들 때 확정된 유형을 최대한 쓰고,
맞는 것이 없을 때만 새 유형을 제안한다. 운영자가 검토 화면에서 받아들일지 정한다. 한 줄 목록이고 나무로 만들지 않는다.

- 마이그레이션 `20261017120000_concept_types.sql`. `concept_types`(이름 고유, 대소문자·앞뒤 공백 무시)는 시범에서 쓴 다섯 가지로 시작한다:
  정의(기존 구분 정의), 성질(정리), 방법(연산), 표현(정의), 주의(정리). 유형마다 기존 구분을 하나 정해 두고, 확정 때 `concepts.sub_type`·`kind`를
  여기서 채운다(학습앱 연산 문제 등 기존 구분을 쓰는 곳은 그대로 동작).
- `concept_type_links`(개념 하나에 유형 하나)로 잇고 `concepts` 표는 바꾸지 않는다. 기존 개념에는 유형을 붙이지 않는다(자동 재분류 없음).
  개념 상세에 "유형: X" 배지(유형이 있는 개념만).
- AI의 새 유형 제안: 이름·설명·기존 구분·거절하면 대신 쓸 확정 유형·이유. 목록에 이미 있는 이름은 제안에서 빼고 목록 표기로 맞춘다.
- 검토: 새 유형마다 "결정 전 / 받아들임 / 거절". 결정 전인 유형을 쓰는 개념이 있으면 확정을 막는다. 거절하면 그 유형을 쓰던 개념을
  AI가 든 가장 가까운 유형으로 바꾸고(카드에서 다시 고를 수 있음), 다시 받아들이면 대신 쓴 유형 그대로인 개념만 되돌린다.
  받아들인 새 유형의 기존 구분은 운영자가 바꿀 수 있다. 받아들인 새 유형은 확정 창에 보이고, 확정할 때만 목록에 더해진다.
- 첫 판(`concept_draft_organize.v1`) 초안의 영어 종류는 기본 유형 이름으로 읽는다(other 는 미정). 유형 없이 저장된 검토는 AI 유형으로 채워
  저장되지 않은 편집으로 보인다(확정 전 다시 저장).
- 유형 이름 바꾸기·지우기·순서 바꾸기 화면은 아직 없다.

### 7.2 검토 창 대화

운영자 결정(2026-10-17): 검토 창 안에서 Think와 이야기하며 추출 결과와 기준을 바꾼다. 바꾸는 것은 모두 승인 카드로 하고,
대화는 하나를 계속 이어 간다(다음 초안에서도). 원하면 새 대화로 바꾼다.

- **대화**: 검토 창 오른쪽(좁으면 "Think" 탭). 교육 부서 대화로 제목은 '개념 초안 검토'. 첫 질문에서 서버가 만들고(`ai_think` `draft_id`,
  `conversation_id` 없음), 앱은 그 id를 계정별로 기억한다(`concept_draft_chat.v1.<uid>`, 개념 탭 대화와 따로). "새 대화"를 누르면 기억만 지우고
  다음 질문에서 새로 만든다. 지난 대화는 Think 화면에 남는다. 개념 탭 대화와 같은 보내기 잠금을 쓴다.
- **보내는 것**: 초안 id만. 보내기 전에 저장하지 않은 검토를 먼저 저장하고(`concept_draft_save_review`), 서버가 보낼 때마다 저장된 초안
  (항목 key·종류·표시·폴더·근거 블록과 쪽, 새 유형, 확정 유형 목록, 라이브러리 영역, 고른 기준의 확정본·저장된 초안, 블록 원문, 뺀 블록)을 다시 읽는다.
  블록 원문은 길면 자른다(블록 600자, 모두 24000자). 서버가 읽은 결과(읽음·잘림·없음·오류·건너뜀·옛 서버)를 패널에 알린다.
  닫힌 초안(확정·버림·다시 정리)은 읽기만 하고 카드를 만들지 않는다. 옛 Edge(`capabilities.concept_draft_reference` 없음)면 보내기를 막는다.
- **항목 key**: 검토 항목마다 `key`(없으면 `c{번호}`, 나눈 항목 `c{번호}.{n}`)가 있고 카드 머리에 보인다. Think도 key로 부른다.
  `blocks`가 있으면 AI 결과의 근거 블록 대신 그 블록이 근거·출처 쪽이 된다. 합친 항목은 빼기 + `merged_into`.
- **카드 세 가지**(`ai_actions`, 제안 `concept_draft_action_propose` · 승인 `concept_draft_action_apply`):
  - `concept_draft_change` 개념 초안 변경: 이름·내용 고치기, 빼기·되살리기, 종류 바꾸기, 새 종류 제안, 폴더 바꾸기, 나누기(2~6개, 근거 블록을 나눔),
    합치기(근거 블록을 모음). 한 카드에 30건까지. 저장된 검토가 있어야 제안하고, 제안할 때 건드린 항목을 카드에 남겨 승인할 때 그 항목이 그대로일 때만
    반영한다(`concept_draft_change_stale`). 승인하면 저장된 검토가 바뀐다(확정은 따로).
  - `concept_criterion_change` 정리 기준 고치기: 이 초안에 쓴 기준만. 승인하면 그 기준의 **초안으로만** 저장한다(확정은 정리 기준 화면). 새 기준은 만들지 않는다.
  - `concept_draft_rerun` 다시 정리: 같은 쪽·같은(또는 고른) 기준으로 새 초안을 만든다(약 $0.09, 전사는 다시 하지 않음). 검토 창에서만 승인한다.
    `concept_draft_organize` task `rerun`이 새 초안(`rerun_of`)을 만든 뒤 `concept_draft_rerun_finish`로 지금 초안을 `replaced`(다시 정리함, `replaced_by`)로
    닫고 카드를 승인됨으로 남긴다. 그사이 카드가 처리됐거나 초안이 닫혔으면 새 초안을 버린다(409). 앱은 이어서 폴더 제안을 만들고 새 초안으로 옮겨 간다.
    지금 검토는 새 초안으로 옮기지 않는다. 닫힌 초안은 목록과 "새 초안 열기"로 다시 연다.
- 검토 창 안에서는 승인 전에 저장하지 않은 검토를 먼저 저장하고, 승인 뒤 초안을 다시 읽는다. 다른 초안의 카드·닫힌 초안의 카드는 승인하지 않는다.
  검토 창 밖(Think 화면)에서는 변경·기준 카드는 바로 승인할 수 있고 다시 정리는 막는다.
- Think는 책 이름·쪽수·원본 위치를 추정해 채우지 않는다. AI가 쓴 기준을 확정 기준으로 등록하지 않는다. 기존 개념·폴더는 바꾸지 않는다.

## 8. 한계와 하지 않은 것

- 기준 변경의 영향 분석과 일괄 재분류. 범위별 검토 기록(§4.5)은 Think 카드로만 남기고, 앱에는 기록을 모아 보는 화면이 아직 없다
  (Think의 `get_concept_review_status`·`get_concept_for_edit`로만 읽는다).
- PDF 자동 분할, 책 합치기, 운영자 확정 없이 AI가 개념·폴더를 만드는 일(한 번에 확정도 운영자가 누를 때만), 확정한 초안으로 기존 개념을 고치거나 합치는 일.
- 쪽 전사의 다시 읽기 버튼(지시문 판을 올리면 새로 읽는다), 20쪽 넘는 소단원 나누기.
- 동시 편집 실시간 반영. 판·초안 시각으로 덮어쓰기만 막는다.
- "같은 개념" 판단 뒤 개념 합치기·출처 옮기기, 관계를 따라 자동 재분류, 이름이 같은 기존 개념에 검토 필요 일괄 표시(같은 이름 검토 창에서 한 쌍씩 판단한다).
- 관계(§4.6): 고리 검사, 옛 `extends`·`special_case`를 새 유형으로 바꾸기, 관계 이력 전체를 모아 보는 화면(상세는 최근 5줄, Think는 20개),
  초안 확정 때 새 유형 고르기(초안은 지금처럼 확장·특수한 경우만).
- 붙은 것이 있는 개념 지우기(강제 삭제·붙은 것 먼저 지우기 없음, §4.4). 개념 표의 만들기·고치기 권한은 아직 로그인한 사용자 모두에게 열려 있다(지우기만 운영자).
- 검토 기록(병합 필요·같은 개념 검토 포함)이 붙은 개념을 정리하는 길: 개념 보관(숨기기)과 붙은 것·기록을 옮기는 안전한 병합은 후속 작업이다(§4.5).
- 앱을 끈 뒤까지 저장하지 않은 입력을 남기는 일.
- 출처 원본 다시 읽기(§4.7): 커서 `ask_think`·부서 협의에서는 쓸 수 없다. 운영 PC 게이트웨이가 꺼져 있으면 이미지 없이 글 자료만 읽는다. 책의 첫 쪽은
  원본 PDF를 받느라 한 번의 기다림(35초) 안에 끝나지 않을 수 있다(그때는 "준비 중"). 쪽 이미지·원본 PDF 디스크 캐시는 지우지 않는다.
  운영 교재는 지금 인쇄 쪽 기록이 PDF 쪽과 다른 출처가 없어(2026-10-23 확인), 쪽이 다른 경우는 시험 DB로만 확인했다.
- 검수 작업(§4.8): 대화를 지우면 그 대화의 카드도 지워진다(`ai_actions` cascade). 초안은 항목에 남아 "카드 사라짐 → 다시 제출"로 보인다.
  기존 `propose_concept_review`는 긴 항목 20개면 카드 크기 한도(60000바이트)를 넘을 수 있다(작업 제출은 45000바이트로 자른다).
  앱에 작업 화면은 없다(Think 대화로만 본다). 자동 이어하기는 부르는 쪽·켜는 RPC가 없다.
