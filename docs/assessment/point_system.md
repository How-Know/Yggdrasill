## 1) 점수와 포인트의 차이

이 둘을 섞으면 나중에 되돌릴 수 없으므로 명확히 구분한다.

| 구분 | 점수(출석/과제) | 포인트 |
| --- | --- | --- |
| 성격 | 현재 상태 지표 | 확정된 재화 |
| 시간 | 감쇠하며 계속 변함 | 지급 후 불변 |
| 저장 | 저장 없이 매번 재계산 | 원장에 영구 기록 |
| 되돌리기 | 자동 | reversal 거래 필요 |

점수 공식은 앞으로도 v5, v6로 계속 바뀐다. 그때마다 포인트를 재계산하면 이미 학생이
사용한 재화와 어긋난다. 따라서 포인트는 **지급 시점의 점수를 스냅샷으로 박아** 확정한다.

## 2) 데이터 구조

- `student_point_ledger` — append-only 원장. 유일한 진실.
  - `delta` 양수는 적립, 음수는 차감
  - `kind` — `earn_attendance` / `earn_homework` / `earn_bonus` / `penalty` /
    `spend_item` / `adjust` / `reversal`
  - `(academy_id, student_id, season_id, kind, source_type, source_id)` 유니크 = 멱등 키
  - `basis` — 지급 근거 스냅샷(그 시점 점수, 배수, 보너스 내역)
  - `rule_version` — 지급 당시 규칙 버전
  - UPDATE는 트리거로 차단. 정정은 `reversal` 거래로만 한다.
- `student_point_balances` — 파생 캐시. 원장 INSERT 트리거로 갱신.
  - `balance` — 사용 가능 잔액. 소비로 줄어든다.
  - `lifetime_earned` — 누적 획득. **레벨/등급 기준값이며 소비해도 줄지 않는다.**
  - `lifetime_spent`, `entry_count`, `last_event_at`

## 3) EXP 부스터

포인트는 RPG의 경험치처럼 감쇠 없이 누적된다. 그래서 "지금 얼마나 잘하고 있나"는
잔액을 깎는 방식이 아니라 **획득 배수**로 반영한다. 총점이 높은 학생은 같은 과제·출석으로
더 많이 적립한다.

```
booster = 0.6 + (총점 / 100) × 1.4        →  0.6 ~ 2.0
```

부스터 입력은 총점 → 출석 점수 → 중립(1.0) 순으로 대체한다. 과제 기록이 아직 없는 신규
학생의 적립을 막지 않기 위한 처리다.

값은 `student_score_cache`에 30분 신선도로 캐시한다. 과제 완료 트리거와 학습앱이
`booster_for_v1`로 **같은 값**을 읽으므로 표시된 배수와 실제 적립 배수가 어긋나지 않는다.

## 4) 적립 규칙 (v4)

### 출석

앱에서 지급한다. 출석 점수와 지각 기준이 앱 계층에만 있으므로 DB에서 계산하지 않는다.

- 대상: 실제 출석이 확정된 기록. 예정(planned)과 결석은 미지급.
- 정시 출석 기본 `20P`, 지각 기본 `12P`
- 부스터 적용 후 정시 `12~40P`, 지각 `7~24P`
- 멱등 키: 출석 기록 id

v1의 출석 전용 배수(`0.8~1.2`)는 폐기하고 부스터로 통합했다. 두 개의 배수 개념을 남겨두면
어느 것이 적용됐는지 추적할 수 없다.

### 과제 완료

DB 트리거에서 지급한다. 품질 지표가 DB에 있고 학생앱 완료 경로까지 함께 커버해야 한다.

- 대상: `homework_items.status`가 완료로 전이될 때 1회
- 단위: **문항**. 기본 `1P`/문항 (난이도 차등은 이후 `points_per_problem`)
- 문항 단가 = `1 + 시간 보너스(최대 0.6) + 검사 보너스(최대 0.4)` → 문항당 `1~2P`
- 하위과제 지급액 = `문항 수 × 단가`, 부스터 적용 후 최소 `1P`
- 멱등 키: 과제 아이템 id (원장은 하위과제 단위, 목록은 그룹으로 합산)

시간 보너스는 빨리 끝낼수록 크다. 레거시(문항 스냅샷 없음)는 0이고, 마이그레이션
과제는 권장시간 안쪽에 끝낸 비율 `(1 - 실측분/권장분) × 0.6`이다. 생성 후 5분 이내
완료나 실측 시간 0은 비정상 속전으로 시간 보너스를 주지 않는다.

검사 보너스는 적게 받을수록 크다. 1회 통과가 문항당 최대 `0.4P`, 2·3회로 줄고
4회부터 `0`. (문항 단가에 붙인 뒤 문항 수를 곱한다.)

검사 1건마다 지급하지 않는 이유는 반복 검사가 곧 포인트 파밍이 되기 때문이다.
완료 시점 1회 확정으로 이 경로를 차단한다.

### 주간 발행량 추정

주 2회 출석, 주 9건 배정 기준이다.

| 프로필 | 총점 | 부스터 | 출석 | 과제 | 합계 |
| --- | --- | --- | --- | --- | --- |
| 성실 | 96.2 | ×1.95 | 78P | 243P | 321P |
| 보통 | 82.0 | ×1.75 | 70P | 144P | 214P |
| 이완 | 62.5 | ×1.47 | 58P | 84P | 142P |
| 방치 | 40.0 | ×1.16 | 46P | 32P | 78P |

부스터 자체의 폭은 1.68배지만 과제 포인트가 부스터와 완료 건수에 동시에 비례하므로
성실/방치 간 격차는 4.1배가 된다. 아이템 가격은 이 수치를 몇 주 관찰한 뒤 정한다.

## 5) 확장 시 지켜야 할 것

- **소비 도입 시**: 잔액 확인과 차감은 하나의 RPC 안에서 행 잠금과 함께 처리한다.
  클라이언트에서 잔액을 계산해 보내면 이중 결제가 발생한다.
- **감점 도입 시**: 잔액을 깎지 말고 `penalty` 음수 거래를 추가한다.
  잔액이 음수가 될 수 있는지 정책을 먼저 정한다(현재 미정).
- **레벨 도입 시**: 반드시 `lifetime_earned`를 기준으로 한다. `balance`를 쓰면 아이템을
  사는 순간 레벨이 내려간다.
- **시즌 도입 시**: `season_id`가 이미 열려 있다. `point_seasons` 테이블을 추가하고
  sentinel을 실제 시즌으로 교체한다.
- **가중치 도입 시**(과정별/난이도별): `basis`에 `book_id`, `grade_label`, `flow_id`가
  이미 기록되므로 과거 데이터로 시뮬레이션한 뒤 다음 규칙 버전을 적용할 수 있다.
- **부스터 곡선 변경 시**: `_booster_from_total_v1`(SQL)과 `PointService.boosterFromTotal`
  (Dart) 양쪽을 함께 고친다. 실제 적립은 서버 값을 쓰고 Dart는 미리보기·대비용이다.

## 6) 소급 수정 정책

출석이나 과제를 나중에 정정해도 **이미 지급한 포인트를 자동 회수하지 않는다.**
학생 입장에서 이유 없이 재화가 사라지는 경험은 제도 신뢰를 깨뜨린다.
회수가 필요하면 관리자가 `reversal` 거래를 명시적으로 남긴다.

## 7) 발행량 관리

원장 구조이므로 `kind`별 기간 합계로 발행량과 소모량을 바로 집계할 수 있다.

- 학생 1인 기준 추정 발행량: 약 `78~321P/주` (성실도에 따라, 위 표 참조)
- 아이템 가격은 최소 4주 실측 후 결정한다.
- 초기에는 소비처를 의도적으로 적게 유지해 인플레이션을 관찰한다.
