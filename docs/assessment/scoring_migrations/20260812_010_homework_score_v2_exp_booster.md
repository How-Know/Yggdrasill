## 왜 바꿨나

v1 과제 점수는 EXP 누적값에서 점수를 역산했다.

```
score100 = 100 * (1 - exp(-expDecayed / 240))     # 반감기 180일
```

누적값에서 상태 점수를 뽑으면 필연적으로 우상향하다 천장에 붙는다. 실제 파라미터로
주 2회·회당 4~5개를 성실히 수행하는 학생의 궤적을 계산해보면 다음과 같았다.

| 경과 | 과제 점수 |
| --- | --- |
| 2주 | 38.9 |
| 1개월 | 64.1 |
| 2개월 | 85.6 |
| 3개월 | 93.6 |
| 4개월 | 96.9 |
| 6개월 이후 | 99 이상 |

두 가지 문제가 있었다.

1. **변별력 소실.** 반년이면 재원생 대부분이 99점대에 몰린다. 총점의 60%가 상수처럼
   굳어서 실제로 움직이는 건 출석 40%뿐이 된다.
2. **감쇠가 사실상 작동하지 않음.** 만점 상태에서 과제를 완전히 끊어도 3개월 뒤 99.9점,
   1년을 놀아도 90점이었다. "약한 희석"을 의도했으나 결과는 준-누적이었다.

근본 원인은 EXP 누적(포인트·레벨에 어울림)과 0~100 상태 점수(총점에 어울림)를 같은
값에서 뽑아 쓴 것이다. v2는 이 둘을 층으로 분리한다.

## 두 층 구조

**스탯 층 (0~100, 누적 아님).** 출석 점수, 과제 점수, 총점. "지금 얼마나 잘하고 있나".
반감기가 있는 것이 정상이다. 최근 성실도를 봐야 부스터가 현재 상태를 반영한다.

**EXP 층 (순수 누적, 감쇠 없음).** 포인트 원장. `lifetime_earned`는 시간이 지나도,
포인트를 써도 줄지 않는다. 획득량 = 기본 XP × 부스터. 부스터는 스탯 층에서 나온다.

이러면 "성실한 학생이 같은 양을 해도 더 많은 EXP를 받는다"가 성립하고, 누적 진행은
절대 깎이지 않는다.

## 과제 점수 v2 산식

평가 단위는 과제 배정(assignment)이다.

**평가 대상 게이트.** 다음 중 하나를 만족하는 배정만 점수에 반영한다.

- `status = 'completed'`
- `due_at < now()`
- `due_at`이 없고 `assigned_at`이 7일 이상 경과

오늘 내준 과제를 아직 안 했다고 감점하면 안 된다. 출석 v3의 "과거 예정 → 결석" 게이트와
같은 사고다. 게이트에 걸려 유보된 건수는 `pending_count`로 노출해 UI가 "기한 전 유보"로
표시한다.

**가중치.** 기준시각은 `coalesce(due_at, assigned_at)`, 즉 "언제 평가되었어야 했나"다.

```
w = exp(-ln2 * 경과일 / 28)        # 반감기 28일 (출석과 동일)
```

**수행 품질 q.**

| 상태 | q |
| --- | --- |
| 완료 | 1.0 |
| 미완료 | `min(0.85, 0.70 * 진행률 + 0.15 * 검사여부)` |
| 미착수(진행 0, 검사 0) | 0.0 |

미완료 상한을 0.85로 둔 이유는 끝내지 않은 과제가 완료와 같아질 수 없기 때문이다.
검사 여부에 0.15를 준 이유는, 검사를 받았다는 것이 교사와 진행 상황을 확인했다는 뜻이라
방치와는 구분되어야 하기 때문이다.

**비율과 스무딩.**

```
ratio = sum(w * q) / sum(w)
유효 가중치 W = sum(w)
W < 8 이면  ratio_adjusted = (ratio * min(W,8) + cohort_ratio * (8 - min(W,8))) / 8
score100 = ratio_adjusted * 100
```

코호트 평균으로 보정하는 이유는 신규 학생이 표본 2~3건으로 0점이나 100점에 튀지 않게
하기 위해서다. 출석 v4.1과 같은 처리다.

**검증 결과.** 프로필별 점수와 시간 불변성.

| 프로필 | 완료/부분/미착수 | 과제 점수 |
| --- | --- | --- |
| 성실 | 95 / 4 / 1 % | 97.0 |
| 보통 | 70 / 20 / 10 % | 80.0 |
| 이완 | 45 / 25 / 30 % | 57.5 |
| 방치 | 20 / 20 / 60 % | 30.0 |

비율이므로 행동이 일정하면 30일·90일·1년·2년 모두 같은 점수를 유지한다. 포화가 없다.

## EXP 부스터

```
booster = 0.6 + (총점 / 100) * 1.4        →  0.6 ~ 2.0
```

부스터 입력은 다음 순서로 결정한다.

1. 총점(출석·과제 근거가 모두 있을 때)
2. 출석 점수(과제 근거가 아직 없을 때)
3. 없으면 `null` → 중립 배수 1.0

신규 학생의 적립을 막지 않으려는 처리다. 하한을 1.0 아래로 둔 것은 저성실 구간에 실질
패널티를 주기 위한 것이지만, 실제로 1.0 미만이 되는 것은 총점 28.6점 아래이므로 드물다.

**적용 지점.**

| 적립 | 기본값 | 부스터 적용 후 |
| --- | --- | --- |
| 정시 출석 | 20P | 12 ~ 40P |
| 지각 | 12P | 7 ~ 24P |
| 과제 완료 | 10 ~ 20P | 6 ~ 40P |

v1의 출석 전용 배수(0.8~1.2)는 폐기하고 부스터로 통합했다. `rule_version`은
`point_rule_v1` → `point_rule_v2`.

**주간 발행량 추정.** 주 2회 출석, 주 9건 배정 기준.

| 프로필 | 총점 | 부스터 | 출석 | 과제 | 합계 |
| --- | --- | --- | --- | --- | --- |
| 성실 | 96.2 | ×1.95 | 78P | 243P | 321P |
| 보통 | 82.0 | ×1.75 | 70P | 144P | 214P |
| 이완 | 62.5 | ×1.47 | 58P | 84P | 142P |
| 방치 | 40.0 | ×1.16 | 46P | 32P | 78P |

부스터 자체의 폭은 1.68배지만, 과제 포인트가 부스터와 완료 건수에 동시에 비례하므로
성실/방치 간 주간 적립 격차는 4.1배가 된다. 아이템 가격은 이 수치를 몇 주 관찰한 뒤
정한다.

**더 벌리고 싶을 때.** 볼록 곡선 `0.6 + 1.4 * (총점/100)^2`로 바꾸면 배수 폭이 2.30배로
늘고 성실/보통 격차가 11.4% → 23.0%가 된다. 지금은 선형을 쓴다. 바꿀 때는
`_booster_from_total_v1`과 `PointService.boosterFromTotal` 양쪽을 함께 고쳐야 한다.

## 부스터 캐시

과제 완료 트리거가 매번 학원 전체 점수를 재계산하면, 교사가 여러 건을 연속 완료할 때
전수 스캔이 그만큼 반복된다. 그래서 `student_score_cache`에 부스터를 캐시한다.

- 신선도 30분. 만료 시 `refresh_student_score_cache_v1`이 전 학생을 한 번에 갱신하므로
  연속 완료 10건에도 갱신은 1회다.
- 갱신 실패는 예외를 잡아 중립 배수 1.0으로 진행한다. 배수를 못 읽었다는 이유로
  적립을 건너뛰면 학생이 손해를 본다.
- 학습앱도 `booster_for_v1` RPC로 **같은 캐시 값**을 읽는다. 표시된 배수와 실제 적립
  배수가 어긋나지 않는다.

## 구조 정리: Dart/SQL 이중 구현 제거

`20260812_009`에서 위험으로 적어둔 항목을 이번에 해소했다. v1은 과제 점수 산식이
`HomeworkScoreService`(Dart)와 `_homework_score_all_v1`(SQL)에 각각 있어 한쪽만 바뀌면
학습앱과 학생앱의 점수가 달라졌다.

v2는 `_homework_score_all_v2`가 유일한 원본이고, 학습앱은 `homework_score_all_v2` RPC를
호출하는 얇은 클라이언트다. 부수 효과로 PostgREST 행 상한 문제도 사라졌다(배정 이력이
수만 행이 되어도 클라이언트가 전량을 받지 않는다).

같은 이유로 `_homework_score_all_v1`은 삭제했다.

## 영향 범위

- `student_get_total_score_v1`이 v2 과제 점수를 쓴다. `formula_version`은 `total_score_v2`.
  가중치(출석 40 / 과제 60)는 그대로다.
- 기존 학생의 과제 점수는 대체로 **내려간다**. v1이 99점대로 포화돼 있었으므로 정상이다.
  실제 수행 비율이 반영된 결과다.
- 총점도 함께 내려간다. 총점의 60%가 과제 점수이므로 포화가 풀린 만큼 조정된다.
- 이미 지급된 포인트는 재계산하지 않는다. 원장은 append-only이고 적립 시점 값으로
  확정된다(`basis`에 당시 부스터가 남는다).

## 사용자 질문에 대한 답

> 총점이 누적식이 아닌거야? 반감기가 있어? 아니면 출석 점수가 깎이면 깎이는거야?

- 총점은 누적이 아니다. 0~100 상태 지표라 구조적으로 누적될 수 없다.
- 반감기는 총점이 아니라 구성요소에 있다. 출석 28일, 과제 28일(v2에서 180일→28일).
- 출석 점수가 깎이면 총점도 깎인다. 비중 40%이므로 출석 10점 하락은 총점 4점 하락이다.
  단 그 결석의 영향은 28일 반감기로 희석되어 시간이 지나면 회복된다.
- 누적식으로 계속 쌓이기만 하는 것은 포인트(`lifetime_earned`)다. 절대 줄지 않는다.
